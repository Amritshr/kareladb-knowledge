KarelaDB knowledge

Documentation of KarelaDB (KARELA DataBase) for people and for AI assistants (web site: https://amritshr.github.io/kareladb-knowledge/): 122 help topics, 25 tutorial chapters and 2306 examples. Every example ran on kareladb 0.2.0-dev when this was built (2026-10-22), and its real result is written under it.

KarelaDB is a SQL database for time-series and relational data, made by Amrit Shrestha. One program serves an HTTP/JSON API and a web console (port 9900) and the PostgreSQL wire protocol (port 8832). It is not kdb+/q.

KarelaDB was called KDB until 2026-10-22; it was renamed so nobody mixes it up with kdb+ by KX Systems. The old kdb command and the KDB_* settings still work.

This repository holds documents and AI skills only. It has no source code of KarelaDB.

Tables

Writing data

  • Line protocol (POST /write): Load many rows fast with the InfluxDB line format over HTTP - one line per row, answered with 204.

Querying

  • SELECT: Choose the columns and values that a query gives back, and the table they come from.
  • WHERE: Keep only the rows you want, with comparisons, IN, BETWEEN, LIKE, IS NULL and time ranges.
  • Operators: Every operator of KarelaDB SQL, which one is done first, and what NULL does to each of them.
  • Joins: Put rows of two or more tables side by side: JOIN, LEFT / RIGHT / FULL JOIN, USING, CROSS JOIN, and ASOF / LT / SPLICE JOIN for time series.
  • GROUP BY and HAVING: Make one row per group (per symbol, per broker, per account) with totals like count, sum and max, and filter the groups with HAVING.

  • UNION and subqueries: Put the rows of two queries together, and use one query inside another.
  • EXPLAIN: See how KarelaDB will read the tables for a query, without running it; with ANALYZE, run it and see what really happened.

  • Candles cookbook: Ready market-data queries: candles from minute data and from trades, daily change, top gainers, volume leaders, 52-week high and low, moving averages and filled gaps.

Functions — date and time

Functions — conditional and NULL

Functions — aggregate

  • Aggregate functions: Make one value from many rows: count, sum, avg, min, max, first, last, median, percentile, vwap, twap, conditional counts and sums, the row of the maximum, and lists of text.

Functions — window and series

Functions — technical indicators

  • Momentum indicators: MACD, stochastic, stochastic RSI, Williams %R, CCI, rate of change, momentum and TRIX on candles, with the same results as TA-Lib.
  • Technical indicators: Moving averages (SMA, EMA, WMA, DEMA, TEMA, TRIMA, KAMA, HMA, VWMA), RSI and ATR on candles, per symbol, with the same results as TA-Lib.
  • Trend indicators: Is the price going up, down or sideways, and how strong is the move? ADX and DI, Aroon, parabolic SAR, Ichimoku, SuperTrend, linear regression and Heikin-Ashi candles.
  • Volatility indicators and bands: How much the price moves: true range, ATR in percent, Bollinger bands, Keltner and Donchian channels.
  • Volume indicators: Is money flowing in or out? On-balance volume, the A/D line, Chaikin money flow and oscillator, MFI, force index and ease of movement.

Functions — statistics

  • Returns and risk: Returns, drawdown, volatility, z-score and the risk numbers of an investment: Sharpe, Sortino, Calmar, information ratio, value at risk and expected shortfall.
  • Statistics functions: Describe a set of numbers: spread (stddev, variance, mad, iqr, range), shape (skewness, kurtosis), other averages (geomean, harmonic_mean, mode) and exact percentiles.

Users & security

  • Users and roles: Database users with passwords, and the roles read, write, ddl and admin for every database or for one.
  • Table rights - GRANT ON TABLE: Give a user rights on one table (GRANT SELECT ON TABLE prices), on some of its columns (GRANT SELECT (id, name) ON staff) or on some of its rows (CREATE POLICY), or take some rights of the role away (REVOKE UPDATE, DELETE ON TABLE ledger).
  • API tokens: Named, revocable secrets for apps - each acts as one user, and DROP TOKEN stops it at once.
  • Two-factor login (TOTP): A database user can log in to the console and POST /api/login with a password and a 6-digit code from an authenticator app.
  • Keeping kareladb serve safe: Keep the server on 127.0.0.1, use users or a token, put HTTPS in front, and pick strong passwords.
  • TLS (https and sslmode=require): Encrypt both ports with one certificate - https:// for the HTTP API and the console, sslmode=require for PostgreSQL clients.
  • Encryption at rest: CREATE DATABASE x WITH (encryption = on) - every file, log record and backup of it is encrypted; without the master key a copied disk shows nothing.
  • Protection - timeouts, limits, safe updates, read-only: Stop slow statements (timeout and cancel), limit the memory of one query and the statements of one user, refuse UPDATE or DELETE without WHERE, and make a database read-only.
  • Audit log: KarelaDB writes security events (logins, users, DDL, backups, refused rights) and, for chosen tables, every changed row with who, when, old and new values.

Backup, check, repair, restore

  • Troubleshooting a running server: What to look at, and what to change, when the server is slow, readers wait, memory or disk grows, the start is slow, a timer or a backup does not run, or data must come back.
  • Backup, check, repair and restore: How KarelaDB keeps your data safe, how to make and test backups, and how to get the data back after damage or a mistake.
  • Backups on a schedule: kareladb serve makes a verified backup of every database at set times, checks a second copy on another disk, runs your command to copy each backup off the server, and warns when the last good backup is old.
  • Versions and upgrades: A new KarelaDB opens the data of an older KarelaDB. An older KarelaDB refuses the data of a newer KarelaDB with "needs a newer KarelaDB" and changes nothing.
  • Standby server: a live read-only copy (--standby-of, kareladb promote): A second KarelaDB server that copies every database of a primary from its log, a moment behind, and serves reads.

Command line

  • The kareladb program: What the kareladb program is, how it finds your databases, and what its exit codes mean.
  • kareladb sql and kareladb shell: Run SQL from the command line once (kareladb sql) or type it at a prompt (kareladb shell).
  • kareladb serve: Start the KarelaDB server - web console, HTTP API, line protocol and PostgreSQL port - on one database or on the whole data folder.
  • kareladb info, check, repair, dump-file: Look inside a database, find damage, repair it, and check one file.
  • kareladb user: Add, list and remove the users of the KarelaDB server, set their passwords and roles, from the command line.

HTTP API

  • HTTP API overview: How to talk to kareladb serve over HTTP - the address, choosing the database, JSON answers, errors, safety rules and limits.
  • Run SQL over HTTP (/exec, /exp): Run SQL with GET or POST /exec and get JSON, or download the rows of a SELECT as CSV with /exp.
  • Databases over HTTP (/api/databases): List the databases of a server, create a new one, and drop one (its folder moves to _trash).
  • Saved queries as URLs (CREATE ENDPOINT): Save a SELECT with named parameters under a name; programs then call GET /v/<name>?param=value and get JSON, without sending SQL.
  • Health, info, check and backup over HTTP: Check that the server is alive, read the tables, disk use and health of a database, look for damage, make and list backups, watch deferred trigger queues, and read the server's memory, processor and settings.
  • Key-value store (Redis-like): GET, SET, INCR, EXPIRE, DEL, KEYS, MGET and the other Redis string commands, hashes, sets, sorted sets, lists (with BLPOP), SORT and WATCH / MULTI / EXEC over HTTP (POST /kv, one command or a pipeline) and as SQL functions (kv_get, kv_set, kv_incr); PUBLISH / SUBSCRIBE and keyspace events. Keys are kept in memory and in the table _kv.
  • Sessions and cursors over HTTP: Keep a transaction open over several HTTP requests with a session, and read a big result a part at a time with a cursor.
  • CSV import over HTTP (POST /imp): Send a CSV file to kareladb serve and it loads the rows, making the table from the file when it is new - QuestDB's /imp.
  • Pinned queries: Pin a SELECT so its result is always ready in the result cache - computed when the database opens, never pushed out, computed again after a write.
  • Change revisions: GET /api/rev and kdb_rev(): A cheap number per table and per symbol that changes when committed rows change, so a chart polls it and reads its candles again only when they changed.
  • Change stream and live subscriptions: changes('t'), GET /api/changes, GET /api/subscribe: Every committed INSERT, UPDATE and DELETE of a table as an ordered stream you can resume from its LSN, in SQL or over HTTP, and queries that push their changed rows.
  • Logins, tokens and roles over HTTP: How a program or the console proves who it is - the access token, HTTP Basic, POST /api/login - and the 401, 403 and 429 answers.

Postgres protocol

  • PostgreSQL protocol (port 8832): Connect to KarelaDB with PostgreSQL tools and drivers - psql, DBeaver, Python, Node, C#, Go - and what works and what does not.
  • PostgreSQL-compatible functions: Functions a PostgreSQL app expects: arrays, sequence numbers (nextval), who you are and what you may do (current_user, has_table_privilege), comments (COMMENT ON), advisory locks and session settings, so app code runs on KarelaDB without changes.
  • pg_stat_activity and pg_stat_statements: See who is connected and what runs now (pg_stat_activity, query_activity(), GET /api/sessions), stop a statement or close a connection (pg_cancel_backend, pg_terminate_backend, CANCEL QUERY, DELETE /api/sessions/<pid>), close idle and vanished clients (idle_session_timeout, tcp_keepalives_*), and see the totals of every statement shape (pg_stat_statements).
  • LISTEN and NOTIFY: Send a message to every client that listens on a channel when a transaction commits - over the PostgreSQL port (LISTEN) or HTTP (GET /listen, server-sent events).
  • Settings - SET, SHOW ALL, ALTER SYSTEM: One list of the server's settings behind pg_settings, SHOW ALL, SHOW PARAMETERS and GET /api/settings; SET for a session, ALTER SYSTEM and pg_reload_conf() for the server.
  • Grafana and Prometheus: Draw KarelaDB data in Grafana through the PostgreSQL port, watch the server with Prometheus, and use the two ready dashboards.
