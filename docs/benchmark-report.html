Benchmark report

How fast KDB is against QuestDB and PostgreSQL on the same PC, and what each engine change of 2026-09-23 gave, including where KDB is still slower and what is not measured.

  • Category: Quality
  • Keywords: benchmark report, benchmarks, speed, performance, how fast, QuestDB, PostgreSQL, KDB vs QuestDB, KDB vs PostgreSQL, rows per second, p50, latency, result cache, memory footprint, disk footprint, full-text search speed, news search, floor sheet, keyless, table locks, group commit, zone maps, saved stats, column mask, warm at open, A/B, index speed, slow parts, known slow, not measured
  • See also: About KDB, Test report, Performance tips, Indexes, Full-text search, PostgreSQL protocol (port 8832), Limits

Every number on this page comes from a report or result file in the KDB source folder, named under each section. Nothing is rounded beyond what those files say.

Two kinds of measurement are on this page:

  • Head-to-head: KDB and another database answer the same question on the same PC, and the answers are compared before the times.
  • KDB-only A/B: the same KDB question before and after one change, the two builds interleaved in the same minutes. These say how much a change gave, not how KDB stands against anyone.

  • Machine: Intel Core i9-14900HX, 32 threads, 32 GB RAM, Windows 11, the same disk for both databases.
  • KDB: 0.2.0-dev, Release build, usually --sync-commits batch (QuestDB does not flush every commit either).
  • Fair rules: the same client for both databases, every write timed until the rows can be read back, and row counts and checksums compared so both answered the same question. A benchmark checks "truncated": /exec answers at most 10,000 rows unless limit is passed.
  • Docker: on 2026-09-23 the opponents ran in throwaway Docker containers, so every request to them crossed Docker Desktop's network. Their single-request numbers are much lower than on 2026-09-12, when they ran natively. Compare within one day, not across days.

News search: KDB vs PostgreSQL

Head-to-head, 2026-09-23. 200,000 articles (a title of 8 words, a body of 250 words, 378 MB of text), 21 runs per query. PostgreSQL 18.6 gets its best practice: a stored tsvector column with a GIN index, searched with the simple configuration (no stemming, like KDB). KDB gets CREATE FULLTEXT INDEX on title and body. Top-20 lists are ranked differently by design (BM25 against ts_rank_cd), so those are compared on row count only.

common word, all 182,571 ids182,571188 ms636 msKDB 3.4x

  • Before the fixes of that day, on 20,000 shorter articles, a common-word count took 351 ms in KDB against 2.5 ms in PostgreSQL. Three faults caused it (a planner that dropped the index for common words, count(*) fetching every row, LIMIT not reaching the index). All three are fixed.
  • The phrase line: word positions were added to the index the same afternoon. The 9.7 ms was measured with a sanitizer build and a fuzz run on the PC; a quiet re-run is owed. The phrase counts differ by 3 rows (2,376 against 2,379) because PostgreSQL also finds a phrase across the end of the title and the start of the body.
  • word + symbol + month is the one line PostgreSQL still wins. KDB now lets the cheaper of the text index and the plain index go first; that is not measured yet.

Where the time of one request goes

KDB-only, 2026-09-23 evening, the container on 9900 through Docker Desktop and a native build on Windows loopback, same minutes:

PathRound trip
the engine alone (server time of SELECT 1)8-10 µs
/exec through Docker Desktop448-800 µs
/health (does nothing) through Docker Desktop465-685 µs
/exec on Windows loopback48-103 µs
a bare Node server on Windows loopback49-80 µs

So the socket path is under 2% of a request through Docker and under 15% on loopback. The rest is Docker Desktop's network and the /exec path itself.
