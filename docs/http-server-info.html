Health, info, check and backup over HTTP

Check that the server is alive, read the tables, disk use and health of a database, look for damage, make and list backups, watch deferred trigger queues, and read the server's memory, processor and settings.

  • Category: HTTP API
  • Keywords: health, /health, monitoring, uptime, api/info, table list, recovery_summary, damaged, last_lsn, api/check, scrub, damage, api/backup, api/backups, api/restore, restore while running, point_in_time, api/databases/swap, swap databases, backup_command, backup folder, --backups, last_backup, server_time_ms, auth_required, api/disk, disk usage, trash_bytes, wal_archive_bytes, api/trigger-queue, trigger queue, deferred trigger, oldest_pending_age_ms, zone_partition_skips, zone_block_skips, slice_reads, slice_cache_hits, slice_cache_bytes, KARELADB_SLICE_CACHE_MB, kdb_slice_reads_total, cache_pinned, cache_verify_checks, cache_verify_mismatches, rev_values, wal_archive_mb, web_dir, help_dir, skill_dir, metrics, /metrics, Prometheus, Grafana, slow queries, slow-query log, api/slow-queries, --slow-query-ms, KARELADB_SLOW_QUERY_MS, trash_purged_bytes
  • See also: HTTP API overview, Backup, check, repair and restore, kareladb info, check, repair, dump-file, Web console (health-box), Grafana and Prometheus

These routes tell you how the server and a database are doing. The web console uses them for its table list and health box.

  • GET /health is for monitoring: it needs no login and never touches data.
  • The other routes work on one database: db=<name> or the header X-KDB-Database (choosing the database).
  • Backups go to the backup folder: _backups in the data folder unless --backups <folder> (or KARELADB_BACKUP_DIR, backup_dir in kareladb.conf) names another (where the settings come from).

GET /health

Syntax:

GET /health

Answers when the server is running. Use it to check that KarelaDB is up (a monitoring script, a load balancer, a start script that waits for the server).

ParameterWhereMeaningDefault
(none)-No database, no login-
Answer fieldMeaning
statusalways "ok": the server is running
readyfalse while the server still opens the default database after a start (a long log replay after a crash, a slow disk); true after that. Requests for that database wait until it is open; other databases answer at once
startingonly while ready is false: what it is doing, like opening the default database 'default': replaying the log, 12 s so far
versionthe KarelaDB version
server_time_msthe server clock: milliseconds since 1970-01-01 UTC
auth_requiredtrue when other requests need a token or a login
logintrue when the data folder has users (the console then shows a login form instead of a token box)
  • Status codes: 200; 503 while the server is stopping (drain). When the server does not run, there is no answer at all (the connection is refused).
  • Notes: /health never needs a token or login, even on a server that has them. It does not open a database, so it stays fast when a database is busy. When every HTTP worker is busy with queries, /health does not wait in line behind them: a thread of its own answers it (plain HTTP; over https it waits for a worker as before).
  • At start: the port answers within about a second, however many databases the data folder holds. Only the default database is opened at start; every other one opens when it is first used. A start script that must wait for the default database waits for "ready": true.

Response:

  "product": "KarelaDB",
  "server_time_ms": 1792825098244,

# Wait until a server that is starting answers (at most 10 seconds).
foreach ($i in 1..50) {
  try { $h = Invoke-RestMethod http://127.0.0.1:9900/health; "KarelaDB $($h.version) is up"; break }
  catch { Start-Sleep -Milliseconds 200 }
}
import requests

try:
    h = requests.get("http://127.0.0.1:9900/health", timeout=3).json()
    print("up, version", h["version"])
except requests.RequestException:
    print("KarelaDB is down")

GET /api/info

Syntax:

GET /api/info[?db=<name>]

Everything about one database: its tables and columns, sizes, damage, what happened when it was opened, and the last backup.

ParameterWhereMeaningDefault
dbURLThe database (or the header X-KDB-Database)the default database
Answer fieldMeaning
databaseThe database name
dirIts folder
versionThe KarelaDB version
opened_msWhen the server opened the database (ms since 1970, UTC)
server_time_msThe server clock
last_lsnThe number of the last change in the log (the LSN, log sequence number). It grows with every change.
data_files, data_bytesCount and size of the data files
tables[]One object per table: name, kind (timeseries or relational), partition (NONE, DAY, MONTH, YEAR), timestamp_column, rows, bytes, columns[], create_sql
tables[].columns[]name, type, primary_key, not_null, computed (a column made from others), references (the table and column it points to, or empty)
damaged[]Damaged files KarelaDB knows about; empty when all is well
recovery_summaryWhat KarelaDB did when it opened the database (for example after a crash)
warningA warning when the data is far bigger than --memory; "" when all is well
backup_dirThe backup folder of this database (empty when backups are off)
last_backupThe newest backup (same fields as POST /api/backup), or null
auth_requiredtrue when requests need a token or login
read_onlytrue when this database only reads
protectionThe server's protection settings: statement_timeout_ms, max_result_bytes, max_groups, max_queries_per_user, safe_updates, running (statements running now), server_read_only, audit
backup_scheduleThe backup schedule and its last run, or null without a schedule
backup_commandThe copy command run after each backup and its last run, or null without one
timersHow many timers of this database are on
  • Status codes: 200; 401/403 login or role (needs read); 404 unknown database; 500 the database cannot be read.
  • Notes: views, functions and procedures are not in tables[]; use SHOW VIEWS, SHOW FUNCTIONS and SHOW PROCEDURES with /exec.

GET /api/disk

Syntax:

GET /api/disk[?db=<name>]

What one database takes on disk, part by part. The console's Keep data page shows it. It walks the trash folder, so it is a separate route and not part of /api/info. It never waits for running statements and never holds them up: while the database is busy writing, the answer is its last measure (each open database measures about once a minute; measured_ms says when).

ParameterWhereMeaningDefault
dbURLThe database (or the header X-KDB-Database)the default database
Answer fieldMeaning
databaseThe database name
data_files, data_bytesThe current version of every file
tail_files, tail_bytesOf those: tail files, rows appended after a partition's file and not yet folded back into it
delta_files, delta_bytesOf those: delta files, rows of a partition replaced or deleted and not yet compacted into it
previous_files, previous_bytesOlder versions kept for repairs (PURGE VERSIONS removes them)
trash_folders, trash_bytesReplaced files waiting in _trash to be removed (PURGE TRASH)
wal_bytesThe log (the WAL)
wal_archive_bytesOld log kept for repairs and restores (WAL_ARCHIVE)
total_bytesAll of the above together
trash_purged_bytesWhat the database removed from its trash by itself since it opened
  • Status codes: 200; 401/403 login or role (needs read); 404 unknown database.
  • Notes: see trash and versions for how to free the space.

GET /api/trigger-queue

Syntax:

GET /api/trigger-queue[?db=<name>][&trigger=<name>][&wait=<time>]

The queues of the database's deferred triggers, and every job that has not finished yet. Use it to see the lag after a load, or to wait until the work of a load is done.

ParameterWhereMeaningDefault
dbURLThe database (or the header X-KDB-Database)the default database
triggerURLOnly this triggerevery deferred trigger
waitURLHold the answer until the jobs finished, or stand still behind a failed job, for at most this long (500ms, 30s, 10min)no wait
Answer fieldMeaning
queues[]One object per deferred trigger (below)
jobs[]Every job not finished yet: id, trigger, table, status, rows, commit_lsn, made_ms, took_ms, error

Each queues object:

FieldMeaning
trigger, table, enabledThe trigger, its table, and whether it is enabled
timeout_msIts DEFERRED TIMEOUT; 0 = the statement timeout
pendingJobs not finished: waiting, running and failed
oldest_pending_age_msHow long the oldest of those has waited: the lag. 0 = none.
running_job, running_since_msThe job running now (same fields as jobs[]), or null
failed_job, failed_msThe job that failed and stopped the queue, or null (recovery)
last_done_jobThe newest job that finished (done or skipped)

A job's status is waiting, running, done, skipped, failed, or blocked (waiting behind a failed job).

  • Status codes: 200; 400 a wait that is not a time; 401/403 login or role (needs read); 404 unknown database, or trigger names no deferred trigger.
  • Notes: GET /api/stats shows the same queues for every open database, under trigger_queues. A load can also wait for its own jobs: POST /write?...&wait=trigger (line protocol).

POST /api/check

Syntax:

POST /api/check[?db=<name>]

Reads every block of every data file and of the log, and checks each against its checksum (a small number that changes when the data is damaged). Use it to find damage early.

ParameterWhereMeaningDefault
dbURLThe database (or the header X-KDB-Database)the default database
Answer fieldMeaning
oktrue when nothing is damaged
files_checkedData files read
bytes_checkedBytes read
wal_segments_checkedLog files read (the WAL, write-ahead log, where every change is written first)
problems[]One text for each problem found; empty when ok
elapsed_usTime it took, in microseconds
  • Status codes: 200 (also when damage is found: then ok is false); 401/403 login or role (needs admin on the database); 404 unknown database; 405 for GET.
  • Notes: a big database takes time, because every file is read. When ok is false: stop the server and run kareladb repair (check, repair, restore). CHECK TABLE name in SQL checks one table.

POST /api/backup

Syntax:

POST /api/backup[?db=<name>]

Makes a verified backup of the database while the server keeps running: it copies the files into a new folder and reads the copy back to check it.

ParameterWhereMeaningDefault
dbURLThe database (or the header X-KDB-Database)the default database
Answer fieldMeaning
nameThe backup's folder name: the time, like 20260911-081748-398
dirThe backup folder: <backup folder>/<database>/<name>
created_ms, createdWhen it was made: ms since 1970, and as UTC text
end_lsnThe last change in the backup
checkpoint_lsnThe last change already in the data files when it was made
files, bytesCount and size of the copied files
  • Status codes: 200; 400 backups are off (no backup folder is set; ...); 401/403 login or role (needs admin on the database); 404 unknown database; 500 disk trouble; 503 busy.
  • Notes: other requests can go on while the backup runs. After each backup, old backups are removed: the newest of each of the last 7 days and of the last 4 weeks are kept (--keep-daily, --keep-weekly). BACKUP DATABASE in SQL (with POST /exec) does the same. A backup on the same disk is lost with that disk: a copy command copies each one off the server.

POST /api/restore

Syntax:

POST /api/restore[?db=<name>]
body: {"as": "<new database>", "database": "<name>", "backup": "<backup name>", "until": "<time>" | "latest", "until_ms": <ms>}

Restores a backup of a database into a new database while the server runs. The database itself is not touched. See restore while the server runs.

FieldMeaningDefault
asThe name of the new database. It must not exist.required
databaseWhose backup (or db= / X-KDB-Database)the default database
backupOne backup's name, from GET /api/backupsthe newest one made before until, else the newest
untilReplay the database's own log up to this time: 2026-09-24 14:05:09 (UTC unless it ends in Z or an offset like +05:45). latest = all of the log.the backup as it was
until_msThe same time in ms since 1970
Answer fieldMeaning
database, sourceThe new database and the one whose backup it is
backupThe backup used (fields of POST /api/backup)
until_ms, used_logThe time asked for (null = none), and whether the log was replayed
opened, open_errorThe new database was opened and its log replayed; false with the reason if not
notesWhat the restore did, like stopped at the requested time: changes after LSN 36 are not restored
took_msHow long it took
nextWhat to do next
  • Needs: the user's own ROLE admin.
  • Status codes: 200; 400 a missing or bad name, a bad until, or no backup older than until; 401; 403; 404 no such database, no backups, or no such backup; 409 the name is taken, or another restore is running; 500 the backup is damaged (pick another one) or a disk problem.
  • Notes: one restore runs at a time. The source keeps taking reads and writes meanwhile; while its log is read, old log files stay in place. It is copied into a hidden folder first and only gets its name when complete, so nobody sees half a database. Each restore is in the audit log (event = 'restore').

POST /api/databases/swap

Syntax:

POST /api/databases/swap[?db=<name>]
body: {"database": "<name>", "with": "<other name>"}

The two databases trade their data, by renaming their folders. Everything KarelaDB keeps by name stays with the name: users' rights, READ ONLY, the dialect, WAL_ARCHIVE, timers and pins. So after a restore into market_check, a swap of market with market_check puts the restored data under market for everyone who uses it, and the old data is in market_check.

  • Needs: the user's own ROLE admin.
  • Status codes: 200 {"swapped": true, "database", "with"}; 400 with missing, the same database twice, or a database served by its path; 401; 403; 404 no such database; 409 one of them is in use (an open PostgreSQL connection, a session, a running request), being opened, or dropped.
  • Notes: both databases are closed for the swap and open again at their next use. The swap is in the audit log (event = 'swap database'). Swap again to undo it.

Checks a folder and writes it to the settings file. Before writing anything the server makes the folder if it is missing, writes and removes a probe file in it, and refuses a folder that is itself one database (it holds a _manifest.a) - the data folder is the one above those. A folder that fails any of these is a 400 with the reason, and the settings file is not touched.

POST /api/restart

Syntax:

POST /api/restart

Closes every database cleanly, then starts the server again in the same process, on the same port. No service manager, Docker restart policy or supervisor is needed.

The reply is sent before the server stops listening, so the caller always gets an answer. Statements that are running are stopped and open transactions rolled back, as at a normal shutdown. The server prints restarting..., then databases closed cleanly, then its usual banner; the restart is written to the audit log.

A folder saved in kareladb.conf that cannot be used when the server comes back does not stop it: the server prints a warning and starts on the usual folder instead.
