Comments and suggestions

How people who use a KarelaDB server send comments, suggestions and problem reports, and how its admins read them.

  • Category: Web console
  • Keywords: feedback, comment, comments, suggestion, suggestions, problem report, bug report, send feedback, contact, POST /api/feedback, GET /api/feedback, POST /api/feedback/<id>, _feedback
  • See also: Web console, Logins, tokens and roles over HTTP, Users and roles, About KarelaDB

Anyone who may use a KarelaDB server can send its admins a comment, a suggestion or a problem report. The message is saved on that server, in the table _feedback, so it survives restarts and is part of every backup.

WhoWhat they can doWhere
anyone who can open the console (logged in, or with the token)send a messageHelp > Comments and suggestions
a server admin (the user's own ROLE admin, or the token)read every message and mark it read or donethe same page, under Received
a programthe same, over HTTPPOST /api/feedback, GET /api/feedback, POST /api/feedback/<id>
  • Messages go to the admins of this server, not to the makers of KarelaDB.
  • A message can be up to 4,000 characters. A name or email for an answer is optional.
  • One user can send at most 10 messages in 10 minutes (without a user name: one client address), so a script cannot fill the table.
  • Messages are kept in the hidden _system database when the server has a data folder, or in the served database when kareladb serve runs on one folder.

The page in the console

Open Help > Comments and suggestions.

  1. Pick what it is: Comment, Suggestion or Problem.
  2. Write the message. Ctrl+Enter sends it too.
  3. Optionally add a name or email, if you would like an answer.
  4. Press Send. The page says which number the message was saved as.

A server admin also sees Received: every message, newest first, with its kind, time, sender and state. New, Read, Done and All filter the list; Mark read, Mark done and Mark new change a message's state.

POST /api/feedback

Syntax:

POST /api/feedback
Content-Type: application/json

{"kind": "comment | suggestion | problem", "message": "...", "contact": "...", "page": "..."}

Saves one message. Needs a login or the token, like every /api route; no role is needed.

FieldNeededRule
kindno (default comment)comment, suggestion or problem
messageyes1 to 4,000 characters, no control characters except line breaks and tabs
contactnoup to 200 characters
pagenowhere it was sent from, up to 200 characters
  • Returns: {"id": 12, "saved": true}.
  • Errors: 400 with a message that says which field is wrong; 401 without a login; 429 after 10 messages in 10 minutes from one user (or one address, for the token).
  • The server adds the time, the user name and the client address itself.
curl -s -X POST "$KARELADB_URL/api/feedback" -H "Authorization: Bearer $KARELADB_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary '{"kind":"suggestion","message":"Please add a CSV export to dashboards.","contact":"ram@example.com"}'

{"id":1,"saved":true}

GET /api/feedback

Syntax:

GET /api/feedback[?status=new|read|done][&limit=N]

Reads the messages, newest first, as columns and rows like /exec. Needs a server admin: the user's own ROLE admin or the token, because messages can hold names and email addresses.

ParameterMeaningDefault
statusonly messages in this state: new, read or doneall
limitat most this many rows; more than 1,000 counts as 1,000100
ColumnTypeMeaning
idLONGthe message number
timeTIMESTAMPwhen it was sent (UTC)
kindSTRINGcomment, suggestion or problem
statusSTRINGnew, read or done
messageSTRINGthe text
contactSTRINGthe name or email given, or NULL
pageSTRINGwhere it was sent from
userSTRINGthe logged-in user, or NULL for the token
clientSTRINGthe client address
  • Returns: {"columns": [...], "dataset": [[...], ...], "count": N}. A server where nobody has sent anything yet answers with no rows.
  • Errors: 400 for an unknown status; 401 without a login; 403 for a user who is not a server admin.

POST /api/feedback/<id>

Syntax:

POST /api/feedback/<id>
Content-Type: application/json

{"status": "new | read | done"}

Changes the state of one message. status can also be a query or form field (?status=done). Needs a server admin, like reading.

  • Returns: {"id": 12, "status": "done"}.
  • Errors: 400 when <id> is not a whole number above 0, or status is not new, read or done; 403 for a user who is not a server admin; 404 there is no message #<id>.
