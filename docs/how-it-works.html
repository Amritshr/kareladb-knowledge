How KarelaDB works

One page on the design of KarelaDB, covering the files on disk, the log and checksums that protect a commit, how a query is run, how writers and readers share the data, and how copies and clusters work.

The pieces

PieceWhat it doesDetail

Checksums

KarelaDB uses CRC32C (Castagnoli) everywhere it must notice a changed bit:

WhereWhat the checksum covers
A log recordThe record header and its payload. It is checked last, so a search through damaged bytes stays fast.
A block of a data fileOne CRC per block, stored in a table at the end of the file. The table has its own CRC.
A file header and trailerEach has its own CRC. A manifest slot and a backup segment are checked too.
A whole fileA digest (a CRC over the header and the CRC table). The manifest stores the digest and the size of every file, and a file is used only if both match.
An encrypted databaseThe CRC covers the encrypted bytes. Each log record is also authenticated (AEAD), so it cannot be moved or changed without being noticed. See encryption.

When a check fails, KarelaDB names the file and block. A damaged data file goes down a repair ladder: an older version of the file, then a backup, then the log. An unrepairable log stops the open unless you choose kareladb repair --accept-log-loss. See backup-and-safety and wal-guarantees.

A commit, in order

  1. The change is written to the log as data records and one commit record, in one buffer. A change never spans two log segments, and the commit record comes last.
  2. The log is flushed (fsync). With the default --sync-commits always, writers that commit at the same moment share one flush (group commit). Each one still waits for its own position in the log.
  3. Only then does the client hear "committed".
  4. A checkpoint later writes the changed tables as new data files, verifies them, flushes the log and folders, saves the manifest, and only then moves the old files to a trash folder.

After a crash the next open reads the log, keeps every change with a complete commit record and drops the rest. Two settings trade safety for speed on purpose (batch and synchronous_commit = off); wal-guarantees says exactly what each can lose. In every mode the database itself is never damaged by a power cut.

How a query runs

StepWhat happens
PlanEXPLAIN shows the plan: which partitions are read, which index is used, which engine runs it (explain).
Skip workPartitions outside the time range are not opened. Zone maps (the minimum and maximum of each column per file and block) skip files and blocks that cannot match a filter. Saved statistics answer count, min and max without reading rows.
Column engineThe common shapes (filters, GROUP BY, SAMPLE BY, some joins) run over columns in chunks of 65,536 rows with a selection vector, using several threads. The sums, minimums and maximums use AVX2 where the CPU has it.
Row engineShapes the column engine does not take run row by row, on one thread. EXPLAIN says engine: row so you can see it.

performance-tips says how to write queries that stay on the column engine.

Writers and readers

  • A writer takes a lock on each table it changes. Writers of different tables run at the same time.
  • On a table with a primary key, SELECT ... FOR UPDATE locks only the rows it returns, and NOWAIT and SKIP LOCKED work (transactions).
  • Readers can be set to read a snapshot, so a long write does not make a SELECT wait (transactions, transactions).
  • Each database has its own log, so one database cannot slow the commits of another.

Copies and clusters

  • A standby follows the primary's log, applies whole transactions in order, and refuses writes. It checks the position of the last transaction on every request, so two copies that have drifted apart stop with an error and never mix (standby).
  • A cluster adds a witness and elections. A new leader starts a new term and a new log timeline, and an old leader that lost its lease is fenced, so two primaries cannot both write (cluster).
  • The change stream gives the same log per table, exactly once, resumable (change-stream).

What the design does not do

  • It does not detect a disk or file system that ignores fsync. Every promise above depends on the flush being real.
  • It is not a kernel-bypass or JIT engine. See hft-and-low-latency for what was measured and what was refused.
  • Known limits are on limits.
