CREATE TABLE

Make a relational or a time-series table, with partitions, sort order, a dedup key, rounded times and computed columns, or make one from a query with CREATE TABLE ... AS.

  • Category: Tables
  • Keywords: create table, new table, IF NOT EXISTS, TEMP TABLE, TEMPORARY, UNLOGGED, table options, relational table, time-series table, timeseries table, RECORDS, TIMESERIES, PARTITION BY, DAY, MONTH, YEAR, NONE, SYMBOL(col), SORT BY, DEDUP KEY, DEDUP UPSERT KEYS, TIMESTAMP(col), WAL, CREATE TABLE AS, CREATE TABLE ... AS SELECT, AS SELECT, WITH NO DATA, copy a table, deduplication, ROUND, round time, computed column, generated column, GENERATED ALWAYS, STORED, stored generated column, virtual column, AS, schema, design, ttl_column, row TTL, expire, EXPIRE, expires_at, per-row TTL, key expiry, redis, session table, rate limit, max_bytes, evict, durability, cache table, LRU, eviction, maxmemory, kv_memory, volatile_ttl
  • See also: Column types, Constraints, ALTER, RENAME and DROP TABLE, SHOW TABLES, COLUMNS, CREATE TABLE, INSERT, Partitions, SORT BY and DEDUP KEY, Indexes

CREATE TABLE makes a new table. KarelaDB has two kinds of tables:

Relational tableTime-series table
Holdslists of things: users, accounts, brokers, postsrows with a time: candles, trades, live prices
Written asCREATE TABLE t (...)CREATE TABLE t (...) TIMESERIES(time_column)
Duplicate checkPRIMARY KEY, UNIQUEDEDUP KEY (..., time)
Split into filesnoPARTITION BY DAY, MONTH, YEAR or NONE

Simple rule: if every row has a time and many new rows come every day, use a time-series table. You cannot change the kind, the partitions or the sort order later, so choose carefully before you load big data. The dedup key can be changed later, but that rewrites every row (DEDUP ENABLE).

Example: Daily stock candles: a time-series table

CREATE TABLE ochl_day (
  time   TIMESTAMP ROUND 1d,
  symbol SYMBOL,
  open   DOUBLE,
  high   DOUBLE,
  low    DOUBLE,
  close  DOUBLE,
  volume DOUBLE
) TIMESERIES(time) PARTITION BY YEAR DEDUP KEY (symbol, time);

Result:

table 'ochl_day' created

CREATE TABLE

Syntax:

CREATE TABLE [IF NOT EXISTS] name (
  column TYPE [PRIMARY KEY [AUTO]] [NOT NULL] [UNIQUE] [DEFAULT expr]
              [REFERENCES table(column)] [ROUND interval] [AS (expr) | GENERATED ALWAYS AS (expr) STORED]
              [[CONSTRAINT name] CHECK (condition)],
  ...
  [, [CONSTRAINT name] CHECK (condition) ...]
)
[TIMESERIES(time_column)]
[PARTITION BY DAY | MONTH | YEAR | NONE [, SYMBOL(column)]]
[SORT BY (column, ...)]
[DEDUP KEY (column, ...)]
[TTL n HOURS | DAYS | WEEKS | MONTHS | YEARS]
[RECORDS]
[WITH (ttl_column = column)]

Makes a table with at least one column. The table options after ) can come in any order, each at most once.

PartMeaning
IF NOT EXISTSa table with this name is already there: do nothing, no error (the old table is not changed)
namethe table name; see names
column TYPEa column and its type
column rulesPRIMARY KEY, AUTO, NOT NULL, UNIQUE, DEFAULT, REFERENCES, CHECK: see constraints
TTLdrop partitions older than this, by itself; see SET TTL
WITH (ttl_column = c)each row expires at the time in column c: see rows that expire
WITH (max_bytes = '64MB', evict = 'lru')a cache table: rows used longest ago go when it is full; see cache tables
ROUND, AS (...), GENERATED ... STOREDsee ROUND, computed columns and stored generated columns
table optionssee the entries below
  • Returns: table 'name' created, or table 'name' already exists with IF NOT EXISTS.
  • Notes: a view and a table cannot have the same name. CREATE TABLE cannot be used inside BEGIN ... COMMIT. To make a table from a query, see CREATE TABLE ... AS.
  • PostgreSQL: CREATE TEMP TABLE makes a temporary table. CREATE UNLOGGED TABLE is refused: every KarelaDB table is written to the log.
  • QuestDB: TIMESTAMP(col) means TIMESERIES(col), DEDUP UPSERT KEYS (...) means DEDUP KEY (...) with dedup_insert = 'upsert' (a plain INSERT replaces the row, as in QuestDB), and WAL / BYPASS WAL are read and ignored. col SYMBOL INDEX [CAPACITY n], and INDEX(col [CAPACITY n]) after the column list, make an index on the column. A SYMBOL's CAPACITY n, CACHE and NOCACHE are read and ignored: KarelaDB sizes its dictionaries itself.

Temporary tables: CREATE TEMP TABLE

Syntax:

CREATE [GLOBAL | LOCAL] TEMP | TEMPORARY TABLE name (...) [table options]
CREATE TEMP TABLE name AS query

A temporary table belongs to one session, as in PostgreSQL:

Who sees itonly the session that made it. For every other session the name does not exist
A table of the same nameis hidden in that session while the temporary one exists; DROP TABLE of the temporary one shows it again
When it goeswhen the session ends (the PostgreSQL connection closes, or the HTTP session ends). Without a session, at the end of the request. A server that stopped with sessions open drops their tables when it starts
What it isan ordinary table under the name pg_temp_<session>_<name>: indexes, INSERT, UPDATE, DELETE, TRUNCATE and ALTER TABLE work as on any table
  • Role: ddl, like CREATE TABLE.
  • Notes: ON COMMIT DROP and ON COMMIT DELETE ROWS are not supported; the table lives until the session ends.

CREATE TABLE ... AS

Syntax:

CREATE TABLE [IF NOT EXISTS] name [(column, ...)] AS query
    [TIMESERIES(time_column)] [PARTITION BY DAY | MONTH | YEAR | NONE]
    [SORT BY (column, ...)] [DEDUP KEY (column, ...)] [RECORDS]
CREATE TABLE name AS query WITH NO DATA

Makes a new table from the result of a query, and copies the rows in. The columns get the names and types of the query's columns. The query may be in brackets: AS (SELECT ...).

PartMeaning
(column, ...)new names for the first columns, in order
table optionsas for CREATE TABLE; without TIMESERIES the new table is a relational table
WITH NO DATAmake the empty table only
  • Returns: table 'name' created with N row(s).
  • Notes:
    • A SYMBOL column of the query stays SYMBOL (as QuestDB copies it). Keys, NOT NULL, defaults, CHECK rules and indexes are not copied.
    • A plain read (SELECT ... FROM one_table [WHERE ...], no join, GROUP BY, DISTINCT, window, ORDER BY or LIMIT) is copied in batches while the source is read, as INSERT ... SELECT writes, so a copy of millions of rows fits the memory limits (5M rows of 10 columns: about 2.4 GB at the peak instead of 9.7 GB, and twice as fast). Other queries keep their whole result first, under max_result_memory. Add them with ALTER TABLE afterwards, or make the table first and INSERT INTO t SELECT ... (see INSERT ... SELECT).
    • PARTITION BY ..., SYMBOL(col) is not accepted here.
    • Two query columns with the same name are refused: name them with AS.

Relational tables (RECORDS)

Syntax:

CREATE TABLE name (column TYPE [rules], ...) [RECORDS]

A table without TIMESERIES is a relational table. The word RECORDS says it explicitly; it changes nothing. Use relational tables for lists of things that you look up by a key and change often: users, accounts, the ledger, brokers, forum posts, news articles.

  • Give it a PRIMARY KEY. Rows are kept in key order, so a lookup by key is fast.
  • Without a key, every INSERT adds rows, also exact copies.
  • For money, add rules like CHECK (balance >= 0); see CHECK.
  • Notes: PARTITION BY, SORT BY and DEDUP KEY are only for time-series tables. RECORDS together with TIMESERIES is an error.

TIMESERIES

Syntax:

CREATE TABLE name (...) TIMESERIES(time_column) [PARTITION BY ...] [SORT BY (...)] [DEDUP KEY (...)]

Makes a time-series table. time_column is its time column: a stored TIMESTAMP or DATE column. Time-series tables are made for many rows with a time: they are split into files by time (PARTITION BY), and they work with SAMPLE BY, LATEST ON, ASOF JOIN and WHERE time IN '2026-09'.

  • Every row needs a value in the time column.
  • A time-series table cannot have a PRIMARY KEY. Use DEDUP KEY.
  • Notes: partitions use the UTC date of the time column.

Example: Minute candles and live prices

CREATE TABLE ochl_minutes (
  time TIMESTAMP ROUND 1m, symbol SYMBOL,
  open DOUBLE, high DOUBLE, low DOUBLE, close DOUBLE, volume DOUBLE
) TIMESERIES(time) PARTITION BY MONTH DEDUP KEY (symbol, time);

CREATE TABLE live_data (

PARTITION BY

Syntax:

PARTITION BY DAY | MONTH | YEAR | NONE

A time-series table keeps its rows in one file (a partition) per day, month or year of the time column. The default is DAY.

ValuePartition namesGood for
DAY'2026-09-10'trade log trades, live prices: many rows per day
MONTH'2026-09'minute candles
YEAR'2026'daily candles
NONEone partitionvery small time-series tables

Add , SYMBOL(column) after YEAR, MONTH or NONE to split each partition again, one file per symbol: PARTITION BY YEAR, SYMBOL(symbol). The rules are in PARTITION BY ..., SYMBOL(col).

Why partitions help:

  • WHERE time IN '2026-09' reads only the files of September 2026.

  • ALTER TABLE t DROP PARTITION '2025' deletes a whole year at once (DROP PARTITION).

  • Notes: the choices are DAY, MONTH, YEAR and NONE; there are no weekly partitions, and PARTITION BY WEEK is an error. The partition is the UTC date. 2026-09-10T02:00:00+05:45 is 2026-09-09 20:15 UTC, so it goes into the partition 2026-09-09. Too small partitions (DAY for a table with 50 rows a day) make many tiny files; too big ones (NONE for millions of rows) make writes slower. See partitions and dedup.

Setup:

CREATE TABLE ochl_minutes (time TIMESTAMP, symbol SYMBOL, close DOUBLE) TIMESERIES(time) PARTITION BY MONTH;

SORT BY

Syntax:

SORT BY (column, ...)

The order of the rows inside each partition file. Rows with the same first columns are stored close together, so a query for one symbol reads less.

  • Default: the first SYMBOL column, then the time column: SORT BY (symbol, time). Without a SYMBOL column: the time column only.
  • Only stored columns (not computed ones), each once.
  • Notes: you cannot change SORT BY later. Columns in SORT BY cannot be dropped. SHOW CREATE TABLE shows the sort order KarelaDB uses.

DEDUP KEY

Syntax:

DEDUP KEY (column, ..., time_column)

The columns that make two rows "the same row". It is the key of a time-series table, and it must include the time column.

StatementThe key is newThe key is already there
INSERTrow addederror, nothing saved
INSERT OR REPLACErow addedthe old row is replaced
INSERT OR IGNORErow addedthe new row is skipped
  • Without a DEDUP KEY, KarelaDB keeps every row, also exact copies.
  • NULL counts as a value here: two rows with the same time and symbol NULL are the same row.
  • Tip: give every time-series table a DEDUP KEY. Then an import file can be loaded twice without double rows.
  • Notes: QuestDB's DEDUP UPSERT KEYS(...) is read as DEDUP KEY (...) and, as in QuestDB, a plain INSERT of a key that is there then replaces the row (dedup_insert). With KarelaDB's own DEDUP KEY, duplicates give an error unless you write INSERT OR REPLACE, the table has dedup_insert = 'upsert', or the database uses the QuestDB dialect. See INSERT.
  • Notes: a load over the line protocol does less work when every SORT BY column is in the DEDUP KEY (how loads find duplicates).

ROUND

Syntax:

column TIMESTAMP ROUND interval
interval: number + ms | s | m | h | d | w      (1m, 5m, 15m, 1h, 1d)

Cuts every time down to the interval when a row is written. ROUND 1m turns 11:05:42 into 11:05:00. Use it for candles, so that times are clean and the DEDUP KEY finds the same minute or day.

UnitMeaning
msmilliseconds
sseconds
mminutes (also M: ROUND has no months)
hhours
ddays (UTC)
wweeks of 7 days, counted from 1970-01-01 (a Thursday)
  • NULL: a NULL time stays NULL.
  • Notes: only for TIMESTAMP columns. ROUND 1d rounds to the UTC day: 2026-09-10T02:00:00+05:45 becomes 2026-09-09T00:00:00Z. For weeks that start on Sunday, use ROUND 1d and SAMPLE BY 1w in queries instead of ROUND 1w.

Computed columns: AS (expr)

Syntax:

column TYPE AS (expression)

A computed column is not stored. KarelaDB works it out from the other columns of the same row each time you read it.

  • The expression uses stored columns of the same row, operators and built-in functions.
  • You cannot give it a value in INSERT, and UPDATE cannot set it. Change the columns it is made from.
  • INSERT INTO t VALUES (...) without a column list skips computed columns.
  • To keep the value on disk (for an index, UNIQUE or NOT NULL), use a stored generated column.
  • Notes: a computed column cannot also have PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT, REFERENCES or ROUND, and cannot be in SORT BY, DEDUP KEY, a CHECK or an index. No subqueries, window functions or other computed columns inside. Do not use random functions (gen_random_uuid()) or now() in it: the value changes on every read.

CREATE TABLE trade_log (

Stored generated columns: GENERATED ALWAYS AS (expr) STORED

Syntax:

column TYPE GENERATED ALWAYS AS (expression) STORED
column TYPE GENERATED ALWAYS AS (expression) [VIRTUAL]

The PostgreSQL form. With STORED, KarelaDB works the value out when the row is written and keeps it like any other column. Without STORED (or with VIRTUAL) it is a computed column, worked out when read.

AS (expr), VIRTUALSTORED
worked outon every readon every write
takes disk spacenoyes
an index, UNIQUE, NOT NULL, CHECK, REFERENCESnoyes
  • Every write works it out again: INSERT, UPDATE of a column it reads, ON CONFLICT DO UPDATE, a foreign key ON UPDATE CASCADE, and API and line-protocol inserts.
  • You cannot give it a value in INSERT or UPDATE, as in PostgreSQL. INSERT INTO t VALUES (...) without a column list skips it; COPY without a column list too.
  • ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED fills it in for the rows already in the table (the rows are written again).
  • Notes: it cannot be the PRIMARY KEY, a time-series table's time column, or in SORT BY, and cannot have DEFAULT, AUTO or ROUND. It can be in a DEDUP KEY: date_trunc('minute', time) there makes seconds of one minute the same row (a key on the minute). The expression uses stored columns that are not generated themselves, and built-in functions only. A column it uses cannot be dropped first.
  • Tables made before 2026-09-24 with STORED keep a computed column (worked out when read). To store it, drop the column and add it again.

Rows that expire: WITH (ttl_column = ...)

Syntax:

CREATE TABLE name (..., expires_at TIMESTAMP, ...) WITH (ttl_column = expires_at)

Each row can have its own end of life, like a Redis key with EXPIRE. When the time in expires_at has come, the row is gone at once for every statement, and a background thread deletes it within about a second. Use it for login sessions, rate-limit counters, caches and short-lived tokens.

expires_at isthe row is
later than nowthere
now or earliergone: no SELECT, join, UPDATE or DELETE sees it
NULLthere for ever
  • An INSERT of an expired row's key is a new row, not an "already exists" error. INSERT ... ON CONFLICT DO UPDATE starts a fresh row, so a counter that expires counts from 1 again.
  • To keep a row alive longer, UPDATE its expires_at.
  • The deletes are ordinary deletes: they are in the log, and DELETE triggers see the rows.
  • Notes: the column must be a stored TIMESTAMP. It cannot be dropped while the table has the option, and the option is set by CREATE TABLE only (ALTER TABLE ... SET (ttl_column = ...) is refused for now). A database with such a table needs KarelaDB 2026-09-25 or later (versions).
  • Speed: a read of such a table checks the time on each row and never comes from the result cache. The table's TTL n DAYS (whole partitions) is a different, older option: SET TTL.

CREATE TABLE sessions (
  token      STRING PRIMARY KEY,
  user_id    LONG,
  hits       LONG,

SELECT token, user_id FROM sessions ORDER BY token;

  ON CONFLICT (token) DO UPDATE SET hits = sessions.hits + 1 RETURNING hits;

Cache tables: WITH (max_bytes, evict, durability)

Syntax:

CREATE TABLE name (key ... PRIMARY KEY, ...)
  WITH (max_bytes = '64MB' [, evict = 'lru'] [, durability = 'none'])
ALTER TABLE name SET (max_bytes = '128MB')
ALTER TABLE name RESET (max_bytes)

A cache table has a memory cap, like Redis with maxmemory. When its rows take more than max_bytes, a background thread deletes rows until it fits again (within about a second), in the order evict says:

evictRows that go firstRedis name
'lru' (the default with a cap)the rows read or written longest agoallkeys-lru
'volatile_lru'the same, but only rows that expirevolatile-lru
'random'any rowsallkeys-random
'volatile_random'any rows that expirevolatile-random
'volatile_ttl'the rows that expire soonestvolatile-ttl
'none'nothing (no cap)noeviction
OptionMeans
max_bytesthe cap: '64MB', '512KB', '1GB' or a number of bytes; 0 = no cap
durability = 'none'the table is emptied every time the database opens (Redis appendonly no), for data you can rebuild
durability = 'log'rows survive a restart (the default)
  • SELECT kv_memory('name') answers the bytes the table holds, as last measured. A row counts the bytes of its values (text by its length, numbers and times 8 bytes) plus 48 bytes.
  • A row is "used" when a statement reads it row by row (a look-up by key, SELECT ... WHERE) or writes it. Aggregates over many rows (count(*), sum) do not count as a use.
  • Needs: a PRIMARY KEY for any evict; a ttl_column for the volatile_ ones. The evicting deletes are ordinary deletes: they are in the log and DELETE triggers see them.
  • The key-value store has the same cap: CONFIG SET maxmemory 64mb (kv).
  • A database with a cache table needs KarelaDB 2026-10-02 or later (versions).
