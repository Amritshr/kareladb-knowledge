Logins, tokens and roles over HTTP

How a program or the console proves who it is - the access token, HTTP Basic, POST /api/login - and the 401, 403 and 429 answers.

  • Category: HTTP API
  • Keywords: login, logout, api/login, api/logout, api/me, api/session, whoami, token, --token, Bearer, Authorization, HTTP Basic, curl -u, cookie, kdb_login, kdb_auth, kdb_token, CSRF, X-KDB-CSRF, remember me, HttpOnly, SameSite, 401, 403, 429, Retry-After, WWW-Authenticate, roles, read, write, admin, password, session token, failed logins
  • See also: Users and roles, Keeping kareladb serve safe, HTTP API overview (auth), kareladb user, PostgreSQL protocol (port 8832) (passwords)

A server can be open, need a token, or need a user login. This page shows how to send each one over HTTP.

ServerLogin needed?
kareladb serve on 127.0.0.1 (the default), no --token, no usersNo. Only programs on the same computer can connect.
started with --token <secret>Yes: the token. It may do everything.
the data folder has users (CREATE USER, kareladb user add)Yes: a user name and password, or a login token. Each user may do only what their role allows. With --token too, the token also works.
--bind 0.0.0.0 (not 127.x) without --token and without usersthe server does not start
  • GET /health, POST /api/login, POST /api/session, POST /api/logout and the console page need no login. /health says auth_required and login (users exist).
  • Making users and roles: users and roles. Keeping a server on the internet safe: server security.
  • Tutorial: chapter 16, users, passwords and security.

The examples below that need users or a token run on their own new kareladb serve (a fresh data folder), so you see the real answers. On a new server without users, the first CREATE USER ... ROLE admin can be sent without a login; from then on every request needs one.

Ways to send a login

HowSendGood for
The access tokenheader Authorization: Bearer <token>a server started with --token
HTTP Basicheader Authorization: Basic <base64 of user:password> (curl -u user:password)scripts. A good password is remembered for 10 minutes, so it is not slow.
A login tokenPOST /api/login once, then Authorization: Bearer <token>apps that make many requests
An API tokenCREATE TOKEN app FOR USER u once, then Authorization: Bearer kdbt_... (API tokens)apps and services: many named tokens, each revoked on its own
The login cookiePOST /api/login sets the cookie kdb_loginbrowsers: the web console
The token cookiePOST /api/session turns a token into the cookie kdb_authbrowsers: the web console, when you paste a token
  • Base64 is a way to write any bytes as plain letters; curl -u and every HTTP library do it for you.
  • A cookie is a small value the browser keeps and sends back by itself. KarelaDB's cookies are HttpOnly (JavaScript in the page cannot read them) and SameSite=Strict (other web sites cannot make the browser send them).
  • A change sent with a cookie (not a GET) also needs the header X-KDB-CSRF. See CSRF. A header login needs nothing extra.
  • On a server that needs no login, the Authorization header is not checked at all.

POST /api/login

Syntax:

POST /api/login
body: {"user": "<name>", "password": "<password>"[, "code": "<6 digits>"]}
   or user=<name>&password=<password>[&code=<6 digits>]  (Content-Type: application/x-www-form-urlencoded)

Checks a user name and password. On success it starts a login session (12 hours), sets the cookie kdb_login, and gives back a token for Authorization: Bearer <token>.

ParameterWhereMeaningDefault
userJSON body or form fieldThe user name (case is ignored)required
passwordJSON body or form fieldThe passwordrequired
codeJSON body or form fieldThe code of the authenticator app, for a user with two-factor login-
X-KDB-ConsoleheaderSent by the web console: then the answer has no token (the console uses only the cookie)not sent
Answer fieldMeaning
userThe user name as it is stored
roleThe user's own ROLE: admin, write, read or none (for every database)
grantsRoles on single databases, like {"shop": "write"}
expires_msWhen the login ends (ms since 1970, UTC)
tokenThe login token (43 characters). Send it as Authorization: Bearer <token>.
csrfThe X-KDB-CSRF value for changes sent with the cookie (CSRF)
header Set-Cookiekdb_login=<token>; Path=/; HttpOnly; SameSite=Strict; Max-Age=43200 (and Secure over TLS, or when a proxy sends X-Forwarded-Proto: https)
  • Status codes: 200 logged in; 400 no user name, or the server has no users; 401 {"error": "wrong user name or password", "login": true} (the same text for an unknown user, so nobody can find out which names exist); 403 the request comes from another web site; 429 too many failed logins, with a Retry-After header (seconds to wait).
  • Notes:
    • A login ends after 12 hours, at POST /api/logout, or when the user gets a new password or is dropped. A server restart does not end it: logins are kept in the data folder, as hashes only (where).
    • KarelaDB keeps only the SHA-256 of the token, never the token itself.
    • After 5 failed logins for one user from one address, that user must wait before the next try from that address: 1 s, 2 s, 4 s, ... up to 15 minutes. A good login ends the waiting for that user.
    • After 20 failed logins for one user from all addresses together, that user waits everywhere (someone is guessing from many machines).
    • Only the user who failed waits. Other users, and the right --token (with any name, on the PostgreSQL port too), still work from the same address. This matters behind Docker or a NAT, where every client has the same address.
    • Every failed login is printed in the server's output with the user name and address (never the password).
    • The same users log in on the PostgreSQL port.

POST /api/logout

Syntax:

POST /api/logout

Ends a login session: the one of the Authorization: Bearer <token> header, and the one of the kdb_login cookie. It also ends the console session of the kdb_auth cookie on the server, and tells the browser to forget the cookies kdb_login and kdb_auth.

ParameterWhereMeaningDefault
Authorization: Bearer <token>headerThe login token to end-
kdb_logincookieThe login cookie to end-
Answer fieldMeaning
logged_outalways true
header Set-Cookiekdb_login=; Path=/; HttpOnly; SameSite=Strict; Max-Age=0 and the same for kdb_auth (removes the cookies)
  • Status codes: always 200, also when there was no login.
  • Notes: after logout the token answers 401 the login token is wrong or has expired; log in again (POST /api/login). HTTP Basic has nothing to log out: just stop sending the password. The --token cannot be logged out.

The access token (--token)

Syntax:

kareladb serve --token <long random secret>
Authorization: Bearer <token>

The simplest protection: one secret for everything. Whoever sends it may do everything, like an admin.

SituationAnswer
no token sent401 {"error": "access token required"}
a wrong token401 {"error": "wrong access token"}
the right tokenthe normal answer
  • The 401 answer has the header WWW-Authenticate: Bearer realm="kdb".
  • The web console asks for the token once and hands it to POST /api/session. The server keeps the token and gives the browser an HttpOnly cookie with a random session id, so no script in the page can read the token, and the cookie never holds it. CSV downloads work with that cookie too.
  • Older consoles kept the token in the browser's storage and in a cookie kdb_token. The new console moves it into the HttpOnly cookie once and deletes both. The server still reads kdb_token for one more release.
  • The token is compared in constant time, so it cannot be guessed by measuring answer times.
  • It is also the password of the PostgreSQL port when there are no users.
  • Pick a long random token (20 or more characters). For programs that should only read, or only use one database, use users instead.

POST /api/session

Syntax:

POST /api/session[?remember=1]
Authorization: Bearer <token>

Starts a console session for a token and gives the browser the cookie kdb_auth. The web console calls it when you paste a token. The server keeps the token in its memory; the cookie holds only a random session id. The cookie is HttpOnly, so no script in the page can read it.

ParameterWhereMeaningDefault
Authorization: Bearer <token>headerThe --token, an API token or a login tokenrequired
rememberquery1: the session lasts 30 days. Without it the session lasts 12 hours, and the browser forgets the cookie when it closes.not sent

A console session ends when:

What happensWhy
its time is up (12 hours, or 30 days with remember)a forgotten browser does not stay logged in
POST /api/logout with the cookiethe server forgets the id: a copied cookie stops working too
the pasted token stops working (DROP TOKEN, an ended login)the session has the token's rights, checked on every request
the server restartssessions live in memory only: paste the token again
  • A cookie from an older KarelaDB held the token itself. The server no longer takes it: the console asks for the token once more.
Answer fieldMeaning
userThe token's user, or null for the --token
roleThe role; admin for the --token
full_accesstrue for the --token
remembertrue when the cookie is kept 30 days
csrfThe X-KDB-CSRF value for changes sent with the cookie (CSRF)
header Set-Cookiekdb_auth=<session id>; Path=/; HttpOnly; SameSite=Strict (with Max-Age=2592000 for remember, and Secure over TLS)
  • Status codes: 200; 400 no Authorization: Bearer header; 401 a wrong token; 403 the request comes from another web site.
  • Notes: programs do not need it. They send Authorization: Bearer <token> with every request. POST /api/logout makes the browser forget the cookie.

CSRF: the X-KDB-CSRF header

A browser sends cookies by itself, even when another web site makes it send a request. That is called CSRF (cross-site request forgery). So a request that logged in with a cookie and changes something must also send the header X-KDB-CSRF.

RequestNeeds X-KDB-CSRF?
GET or HEAD (only reads)no
POST, PUT, DELETE with the cookie kdb_login or kdb_authyes
any request with Authorization: Bearer or Basicno: another web site cannot set that header
the old cookie kdb_tokenno, but the request must come from the console (X-KDB-Console)
  • The value comes in the csrf field of POST /api/login, POST /api/session and GET /api/me. Another web site cannot read it.
  • The value belongs to the cookie. A new login gives a new value.
  • The web console sends it by itself (window.KdbConsole.api).
  • Without it the answer is 403 with "csrf": true.

Authorization: Basic <base64 of name:password>
curl -u <name>:<password> ...

Sends the user name and password with every request. KarelaDB checks the password once and then remembers it for 10 minutes, so it stays fast.

  • Good for scripts and tools that cannot keep a token.
  • A wrong password: 401 wrong user name or password. Many wrong passwords: 429 with Retry-After.
  • On a server with users, a request with no login gets WWW-Authenticate: Basic realm="kdb", so a browser shows its own password box. The console sends X-KDB-Console: 1 and gets Bearer instead (no browser box).
  • On a server without users, Basic is refused: 401 this server has no users yet.

Roles: what each route needs

Each user has a role: none, read, write or admin. The user's own ROLE counts for every database; a GRANT ... ON DATABASE gives a role on one database. KarelaDB uses the stronger of the two.

RouteNeeds
GET /health, POST /api/login, POST /api/logout, the console filesnothing
GET /api/me, POST /session, DELETE /session/<id>, POST /api/feedbackany login
/exec and /exp with SQL that reads, BEGIN/COMMIT/ROLLBACKread on the database
GET /api/info, GET /api/disk, GET /api/backups, GET /api/trigger-queue, GET /api/stats, GET /api/timers, GET /api/pins, /cursorread
/exec with INSERT, UPDATE, DELETE, CALL; POST /write, POST /imp into a table that is therewrite
/exec with CREATE/ALTER/DROP of tables, views, functions, procedures, triggers, indexes; BACKUP DATABASE, CHECK TABLE; POST /api/check, POST /api/backup; a new table with POST /imp; saving, running and removing timers; pinning and unpinning statementsadmin on the database
POST /api/databases, DELETE /api/databases/<name>, GET /api/settings, POST /api/settings, POST /api/restart, GET /api/audit, GET /api/feedback, POST /api/feedback/<id>, CREATE USER, GRANT, ...the user's own ROLE admin
GET /api/databasesany login; lists only the databases the user may read
  • A session (POST /session) can only be used by the user who opened it.
  • Rights are per database, and per table with table rights; not per column or row.
  • Users with two-factor login send "code" with POST /api/login; without it the answer is 401 with "totp": true.

401, 403 and 429 answers

AnswerMeansWhat to do
401 {"error": "login required: log in (POST /api/login), or send a user name and password (HTTP Basic)", "login": true}no login on a server with userslog in
401 {"error": "wrong user name or password", "login": true}a wrong name or passwordcheck them
401 {"error": "the login token is wrong or has expired; log in again (POST /api/login)"}an old or wrong login tokenlog in again
401 {"error": "your login has expired; log in again"}an old login cookielog in again
401 {"error": "access token required"} / {"error": "wrong access token"}a server with --tokensend the right token
403 {"error": "INSERT needs role write on database 'shop'; user 'report' has read"}logged in, but the role is too weakuse another user, or GRANT
403 {"error": "cross-site requests are not allowed"}a browser request from another sitecall KarelaDB from your backend
403 {"error": "this change came with a login cookie but without the right X-KDB-CSRF header; ...", "csrf": true}a change sent with a cookie but no X-KDB-CSRFsend the csrf value, see CSRF
429 {"error": "too many failed logins; try again in 4 s", "login": true} and Retry-After: 4too many failed loginswait that many seconds

The 403 role message is shown for real in HTTP Basic. In a 401 answer, "login": true tells a program that the server has users (so it should log in, not ask for a token).
