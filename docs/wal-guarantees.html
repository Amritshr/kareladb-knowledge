The log (WAL): what KarelaDB promises

What a commit guarantees after a kill, a power cut or a full disk, how the log, checksums, checkpoint and recovery work, and the known limits of the promise.

  • Category: How it works
  • Keywords: WAL, write-ahead log, log, commit record, LSN, CRC, CRC32C, checksum, fsync, durability, durable, crash, power cut, torn write, torn tail, recovery, checkpoint, manifest, timeline, group commit, sync_commits, synchronous_commit, torn end, log cut, archive, wal_archive, repair, accept-log-loss, ACID, atomic, full disk
  • See also: How KarelaDB works, On-disk file format (version 1), Backup, check, repair and restore, Performance tips, Cluster: automatic failover (--cluster-peers, kareladb witness), Transactions

Written 2026-10-25 from the code. Byte layouts are in the file format sections 4 to 7; this page says what each rule guarantees. Where a sentence says "not checked", the code was not traced to the end and the statement is open.

1. In one paragraph

Every change is first written to the log as records, and the last record of the change is a commit record. A change is committed when its commit record is on disk, and not before. After a crash, recovery reads the log, keeps every change that has a complete commit record and drops the rest. The data files are only a faster copy of the log: a checkpoint writes them, and the log cut (moving old segments to wal_archive/) happens only when no file needs those records any more.

2.3 What "committed" means: the three sync modes

The log is a file that is written and then flushed (fsync). What a client is told, and when, depends on the mode. Statements below are for kareladb serve; the embedded library has the same two options (sync_commits, group_commit in StoreOptions; the C API exposes sync_commits).

ModeHow to get itThe client is told "committed"A crash of the program (kill, out-of-memory kill, docker rm -f)A power cut or operating-system crash
always (default)--sync-commits alwaysAfter the log is flushed to the disk. Writers that commit at the same moment share one flush (group commit); each one still waits for its own LSN to be flushed.Loses nothing that was confirmed.Loses nothing that was confirmed.
batch--sync-commits batchAs soon as the record is written to the log file (handed to the operating system). A background thread flushes at most every sync_interval_ms (10 ms).Loses nothing confirmed: the bytes are in the operating system's cache.Can lose the commits of the last ~10 ms that were confirmed. The database is never damaged: it opens at an older, complete state.
always, with an early answerSET synchronous_commit = off (one session or one request), WITH (synchronous_commit = off) on a table, cache tables and the key-value store's tablesAs soon as the record is in the log buffer; SyncSoon hands it to the file at most once a millisecond and the flusher thread flushes within about 10 ms. A commit that also changes a table that waits is not answered early.Can lose the commits of the last few ms (the ones not yet handed to the file, or made while a flush was running).Can lose about the last 10 ms.

Facts that hold in every mode:

  • The log record is written before the change is applied in memory (in the main write path, the database code, and in the materialized-view refresh, CommitLog comes before ApplyChanges; the flush wait comes later, at the end of the writer), so memory never holds a change the log has no record of, unless the flush itself fails (next point).
  • A checkpoint, a backup and Close always flush the log first (Publish, Close and the backup snapshot call SyncLog). The manifest therefore never names an LSN that is not on disk.
  • If the flush fails for a full disk, the writer cuts the segment back to the last durable point and keeps working (writes get HTTP 507 / SQLSTATE 53100 until there is room). In group commit the rows are already applied in memory and reach the log once space is back; the answer says so, and is not "try again" (a client that sent them again would write them twice).
  • For any other write or flush error the writer stops: later writes fail until the database is reopened, and recovery checks the log. A flush error is never ignored, because after a failed fsync the operating system may have dropped the pages.
  • A change too big for memory (CommitStream, rows spilled to a temporary file) always waits for the disk, whatever synchronous_commit says.
  • On a cluster leader with synchronous standbys, "committed" also waits for a standby to hold the record (cluster); if the leader loses its lease while waiting, the answer is Unconfirmed (the record is on this node's disk, but may be lost).

Open question (not checked): whether a reader on another session can see a change in the few milliseconds between its being applied in memory and the flush, in group-commit mode (the writer gives up its table locks before the flush so that the next writer can share it). If a power cut comes then, that change is lost even though a reader saw it; the writer was never told it was committed.

2.4 The log format and the sync mode

A segment written with group commit or batch is in the batched format (header flag 1): the commit record carries 16 bytes, the commit time and **the highest LSN that was flushed when the record was written**. This is what lets recovery tell a torn end from real damage (2.6). A store that syncs every commit separately (group_commit = false, tests and tools) writes the plain format with 8-byte commit records. A segment is never continued by a store in the other mode: a new segment starts.

A segment is flushed to the disk before the next segment is created, so **only the last segment can have a torn end**. The log is written into a file that was filled with zeros ahead of the records, so a flush writes data only and does not change the file's size on every commit; a zero byte is never a record type, so a reader stops at the zeros.

2.5 Checkpoint

A checkpoint writes the changed tables as new data files, then publishes them (Store::Publish). The order is the guarantee:

  1. Each new file is written as a block file with a checksum on every block and a digest over the file, and re-read and verified (verify_on_publish, on by default).
  2. The log is flushed up to the last LSN (SyncLog).
  3. The folders holding the new files are flushed (SyncDir).
  4. The manifest is saved. It has two slots (_manifest.a, _manifest.b) and each save overwrites the slot with the lower sequence number; the slot being written counts as invalid, so a crash in the middle leaves the other slot whole. The manifest records checkpoint_lsn (every change up to it is in the data files), durable_lsn (the log holds everything up to it) and, for every file, the LSN it holds.
  5. Only after the manifest is durable do the old files move to _trash/ (after about an hour they are deleted), and old log may be archived.

A crash between any two steps leaves either the old manifest (old files, all log intact) or the new manifest (new files, all verified). Files that no manifest lists are moved to _trash/<ms>-unused/ at the next open.

2.6 Recovery (what the next open does)

  1. Read both manifest slots and use the valid one with the higher sequence number.
  2. Load the data files; a damaged one goes down the repair ladder (older version, then backup).
  3. Replay starts at replay_after = min(checkpoint_lsn, LSN of every current file). The whole log from there is checked first and replayed second, so nothing is applied from a log that turns out damaged.
  4. Every transaction with a valid commit record is applied, in LSN order. Data records with no commit record at the end are not committed; they are cut off.
  5. Torn end versus damage. A bad record in the last segment is a torn end (a power cut wrote the pages in any order) unless a later valid record proves otherwise: in a plain segment, a record of a newer transaction; in a batched segment, a **commit record that says the bad record was already flushed**. Only then is it damage. A bad record in an earlier segment is always damage, because that segment was flushed completely before the next one was made.
  6. Damage in a range that is already in the data files is a note only. Damage in records that must be replayed is Corruption: the open stops with the byte and the LSNs. The ways out are a backup (kareladb restore), a repair that fills the range from a backup, or kareladb repair --accept-log-loss.
  7. The log writer then continues the last segment from its last valid byte (and drops the torn bytes) if that segment is whole, in the current timeline and in the same sync mode; otherwise a new segment starts. The manifest is saved with durable_lsn = last LSN before the writer creates anything.

There are four different cuts; they are easy to mix up.

A timeline is the log's history. A restore, a repair that cuts the log and a cluster leader's new term each start a new timeline in a new segment. A segment whose owner is not in the manifest's history belongs to another database or to a history that was dropped, and is never replayed.

4. Known limits of the guarantee

  • durable_lsn is saved at a checkpoint and at close, not at every commit. After a crash, damage to the very last transactions with no newer valid record after them looks exactly like an unfinished write and is dropped (file format, "Known limit"). In always mode those were confirmed to clients, so this needs both a crash and damage of the log's last bytes.
  • A disk or file system that does not honor fsync (some virtual disks, write caches without power-loss protection) breaks every promise above. KarelaDB cannot detect it.
  • batch and the early-answer settings trade durability for speed on purpose; the numbers are in performance tips.
  • The data folder's own checks (kareladb check, scrub) read the log of older segments only when asked (check_all_segments); a normal open does not read segments that every data file already covers.
