The kdb program

What the kdb program is, how it finds your databases, and what its exit codes mean.

  • Category: Command line
  • Keywords: command line, CLI, kdb.exe, usage, exit code, $LASTEXITCODE, data folder, KDB_DATA_DIR, --data-dir, --config, kdb.conf, database name, folder path, --help, -h, --version, kdb help, kdb help tutorial
  • See also: kdb sql and kdb shell, kdb serve, kdb info, check, repair, dump-file, kdb user, Backup, check, repair and restore, Databases and the data folder

kdb is the one program you need. It runs SQL, the interactive shell, the server, backups and repairs. It works in PowerShell, CMD, bash and zsh, on Windows, Linux and macOS.

A database is a folder on the disk. Many databases can live in one data folder (one sub-folder per database). Most commands take a <db> argument: the name of a database in the data folder, or the path of a database folder.

kdb help

Syntax:

kdb
kdb help
kdb --help
kdb -h
kdb help <topic>
kdb help tutorial [<chapter>]

Prints the version and a short list of every command and option, then the list of help topics - the same pages a running server shows at /help - with their titles. kdb help <topic> prints one topic in the terminal (the Markdown source in a source checkout, the built page as text in a package); a word that is not a topic lists the topics whose name contains it. kdb help tutorial lists the tutorial chapters and kdb help tutorial 17 prints one (the tutorial is part of the source checkout only).

  • Exit code: 0 for kdb help, --help and -h. 1 for kdb with no command, for an unknown command, and for a topic that does not exist.
  • Notes: an unknown command (for example a typing mistake like kdb bakup) also prints this list, with exit code 1. The topics come from the help folder the program finds (help_dir in kdb.conf, KDB_HELP_DIR, next to the program, or the checkout's docs/help/site); without one, only the command list is printed.

  web_dir, help_dir and skill_dir name the folders of the console, the help and the Claude skill
  (else KDB_WEB_DIR, KDB_HELP_DIR, KDB_SKILL_DIR, else web/, help/ and skill/ next to kdb).
--memory <MB>: memory for table data kept loaded (default 512). More is faster on big tables.
--memory-limit <size>: one limit for everything the server holds (table data, unsaved changes,
  indexes, results, caches, what the allocator keeps), like 3GB or 3072 (MB). Near it, memory is
  given back (the result cache too); at it, quick statements still run in a small reserve and
  others get 'memory full' (HTTP 503, PostgreSQL 53200); over it, the running statement that
  holds the most is stopped with 'memory full'. Default: 85% of a container's
  memory limit, else of the machine's memory (env KDB_MEMORY_LIMIT; 0 or off = no limit).
--threads <N>: threads for big queries and writes (default and most: half of the CPU threads).
--cache-mb <MB>: memory for results of repeated queries, all databases together (default 256,
  0 = off; else kdb.conf cache_mb, else env KDB_CACHE_MB). A result is used again only while no
  table it read has changed; a quick one (under 1 ms) is kept when asked twice. Queries with
  random() are never kept; with now() only for a caller that takes an older answer
  (/exec?cache_now_ms=500, SET result_cache_now_ms = 500). One result may use a quarter of it,
  a pinned one three quarters. ALTER DATABASE db SET RESULT_CACHE = '256MB' gives a database
  a space of its own.
--pg-compat on|off: PostgreSQL 14's answers for every database without its own ALTER DATABASE ...
  SET pg_compat (default off; env KDB_PG_COMPAT): 7 / 2 = 3, 1.005 is an exact NUMERIC, a window
  with ORDER BY counts ties together, text sorts like en_US. A session can choose with
  SET kdb.pg_compat = on | off.
--pg-int-division on|off: on the Postgres port, whole number / whole number gives a whole
  number (7 / 2 = 3) as in PostgreSQL (default off; env KDB_PG_INT_DIVISION). A session can
  still choose with SET int_division = integer | float.
--reader-yield on|off: readers do not wait for a long trigger or CALL; they read the last
  committed rows (default on; env KDB_READER_YIELD). Off: readers wait for the writer's statement.
--per-table-reads on|off: a reader waits only for writers of the tables it reads, and not while
  a checkpoint writes its files (default on; env KDB_PER_TABLE_READS). Off: it waits for every writer.
--pin-threads auto|on|off: auto (default): on Linux, inside a CPU quota (docker --cpus, cgroup cpu.max)
  smaller than the CPUs the process may run on, every thread is pinned to the quota's worth of CPUs,
  one per core, and moved back when the quota goes (docker update --cpus); 32 connections on a 2-CPU
  quota of a 32-CPU host no longer run on all 32 and stall when the time is spent. on: each HTTP
  worker, PostgreSQL connection and query thread runs on one CPU of its own, taken in turn from as
  many CPUs as KDB may use, out of the cpuset; background threads stay on those CPUs. off: nothing is
  pinned (env KDB_PIN_THREADS). Ignored on Windows.
--read-only-calls on|off: a CALL of a procedure that changes nothing runs like a SELECT: no table
  locks, no transaction (default on; env KDB_READ_ONLY_CALLS).
--scoped-ddl on|off: CREATE/ALTER/DROP TABLE, INDEX and TRIGGER, TRUNCATE, CREATE TABLE AS and
  materialized views lock only the tables they touch; views, procedures and functions lock none
  (default on; env KDB_SCOPED_DDL). Off: every schema change locks every table.
--ddl-beside-writers on|off: with --scoped-ddl, CREATE TABLE, ALTER TABLE, RENAME TABLE and CREATE/DROP
  INDEX run beside a writer of other tables that is inside one long statement (default on; env
  KDB_DDL_BESIDE_WRITERS). Off: they wait until that writer pauses between two statements.
--log-lock-waits on|off: a statement that waits for a table lock longer than --deadlock-timeout
  writes one line to the log naming itself, the lock and who holds it (default off; env
  KDB_LOG_LOCK_WAITS; a session: SET log_lock_waits = on).
--deadlock-timeout 1s: when --log-lock-waits writes its line (default 1s; env KDB_DEADLOCK_TIMEOUT;
  a session: SET deadlock_timeout). Deadlocks are found at once whatever it is.
--skip-locked-beside on|off: SELECT ... FOR UPDATE SKIP LOCKED inside BEGIN reads beside other open
  transactions that hold the table and returns the rows they did not touch (default off; env
  KDB_SKIP_LOCKED_BESIDE). Its UPDATE of such a row waits for their COMMIT. Off: no rows there.
--table-writers one|many: many: several users change one table at the same time when each of their
  statements on it touches single rows by the primary key (one-row INSERT, UPDATE or DELETE ... WHERE
  id = x, a CALL or trigger of such statements); the same row is waited for, as in PostgreSQL. Anything
  else on the table waits for the whole table, as before (default one; env KDB_TABLE_WRITERS).
--snapshot-reads on|off: a reader of a table that a long CALL, trigger job or bulk write is changing
  does not wait: it reads a snapshot of the committed rows (default off; env KDB_SNAPSHOT_READS).
  Tables with an index too, while a writer is busy on them, at any size: the read uses the index
  on the snapshot (an idle BEGIN is taken out and the index used, as before).
--tail-files on|off: a checkpoint saves rows appended after the end of a partition in a small tail file
  instead of writing the whole partition again (default off; env KDB_TAIL_FILES). A database with tail
  files needs a KDB from 2026-10-02 or later (kdb downgrade merges them back).
--snapshot-index-rows 1000000: a table with a full-text/JSON index, or an index not built yet, is
  scanned on a snapshot: only up to this many rows, a bigger one waits for its writer as before
  (default 1000000; 0 = indexed tables never get snapshots; env KDB_SNAPSHOT_INDEX_ROWS).
--txn-spill-mb 64: a transaction's log records past this many MB (or 1/16 of --memory-limit) go to a
  temporary file in the database's _tmp folder until COMMIT (default 64; 0 = never; env KDB_TXN_SPILL_MB).
--lanes on|off: priority lanes (default on; env KDB_LANES). A read whose shape used --heavy-ms of
  CPU or more the last three times it ran is heavy: only --heavy-slots of those run at once, at a
  lower CPU priority, and the rest wait in line. Charts and other short statements never wait. SET kdb.priority = high|normal|low, the X-KDB-Priority header
  and ALTER USER ... SET kdb.priority choose a lane by hand. Off: every statement runs at once.
--heavy-ms 100: the CPU time a read shape must use to count as heavy (env KDB_HEAVY_MS).
--heavy-slots N: heavy statements that run at once (default half the CPUs, at least 1; env
  KDB_HEAVY_SLOTS).
--heavy-queue N: heavy HTTP requests that may wait at once (default half the HTTP threads, at
  least 4; env KDB_HEAVY_QUEUE). Past it a request sent with priority low gets 503; a read heavy by
  its history runs at once. PostgreSQL statements are not counted: they wait up to their timeout.
--read-slots auto|off|N: reads (outside BEGIN) that run at once; the rest wait in line. A read holds
  its slot for at most 10 ms, so a long one never holds the line up (default auto = the CPUs the
  process may use, at least 2, following docker update --cpus; env KDB_READ_SLOTS). Off: every read
  starts at once, as before.
--timezone Asia/Kathmandu: the clock of CURRENT_DATE, ::date, date_trunc, EXTRACT and to_char, and of
  timer and backup schedules (default: the computer's own zone; env
  KDB_TIMEZONE; kdb.conf "timezone"). Times are still stored as UTC. A session: SET TIME ZONE.
  Default: the computer's own zone. Zones with summer time (America/New_York) need the system's
  zone files (tzdata); per user: ALTER USER name SET timezone = 'zone'.
--warm-indexes on|off: build every index right after a database opens, on a background thread,
  so the first query finds them ready (default on; env KDB_WARM_INDEXES). Off: on first use.
--sync-commits always: every write is on disk before it is confirmed (default).
--sync-commits batch: writes are confirmed at once and put on disk every 10 ms. Much faster for
  many small writes; a power cut can lose the last confirmed writes, but never damages the data.

Help topics (0), from ./help-placeholder. "kdb help <topic>" prints one; a running server has them at /help:

kdb version

Syntax:

kdb version
kdb --version
kdb version <db>

Prints the version of KDB and the stored-format features it can read. crc32c hardware: yes means the CPU computes checksums (CRC32C) with special fast instructions. no also works, only slower. With <db> it shows the features that database uses (versions and upgrades).

  • Exit code: 0. With <db>: 3 when the database needs a newer KDB.

<db>: a name or a folder path

Syntax:

kdb sql market "..."          -- a name: the database 'market' in the data folder
kdb sql ./market "..."        -- a path: the folder 'market' in the current folder
kdb sql D:\kdb\market "..."   -- a path: always that folder

The commands sql, shell, serve, info, check, repair and backup take <db>. KDB decides like this:

You writeKDB uses
A name (only letters, digits, _ and -), and the data folder has a database with that nameThat database in the data folder. Upper or lower case does not matter.
A name, and the data folder has no database with that nameThe folder with that name in the current folder. It is created when it does not exist.
A path (it has \, /, : or .)Always that folder. It is created when it does not exist (not by kdb info and kdb check).
Nothing (only kdb shell and kdb serve)The data folder: kdb shell opens the database default; kdb serve serves all databases.
  • Notes: a wrong name does not give an error. kdb sql markett "..." makes a new, empty database markett, and then says table ... does not exist. Write ./market when you want to be sure you mean a folder.
  • With a name, kdb backup and kdb repair --backups use the sub-folder <backups-dir>/<name>, the same place kdb serve uses.
  • Database names are 1 to 64 characters. Market and market are the same database.

The data folder

Syntax:

--data-dir <folder>
KDB_DATA_DIR=<folder>

The data folder holds many databases, one sub-folder per database. KDB looks for it in this order; the first one that is set wins:

#WhereExample
1The option --data-dir <folder>kdb serve --data-dir E:\kdb-data
2Only kdb serve: data_dir in kdb.conf, what the console's Settings page saved (kdb.conf)"data_dir": "E:/kdb-data"
3The environment variable KDB_DATA_DIR$env:KDB_DATA_DIR = "E:\kdb-data"
4The folder data next to the kdb programD:\KDB\build\bin\data
  • --data-dir works with kdb sql, kdb shell, kdb serve, kdb info, kdb check, kdb repair, kdb backup and kdb user.
  • KDB creates the data folder when it is missing.
  • kdb sql, kdb shell and the other commands do not read kdb.conf. When the Settings page moved the server to another folder, give that folder to them with --data-dir.
  • The data folder also holds _trash (dropped databases) and _system (the server's users). They are not databases you can use.
  • Use KDB_DATA_DIR when the data must be on another disk, or when kdb.exe is in a folder where you cannot write (like C:\Program Files).

The log on another disk

Syntax:

KDB_WAL_DIR=<folder>
"wal_dir": "<folder>"        in kdb.conf (kdb serve only)

Every commit writes the database's log and waits for the disk to confirm it. When the data folder is on a slow-to-sync disk (a Windows folder bind-mounted into Docker Desktop confirms a small write in about 1 ms; a Docker volume inside the VM in 0.4 ms), wal_dir puts the log on the faster disk while the data files stay where they are. Each database gets a sub-folder of it, named like the database. KDB leaves a note in the database's own wal folder saying where its log went, so kdb backup, a repair and a server started without the setting still find it. A database that already has a log keeps writing its current segment where it is; the next segment goes to the new folder. The old log kept for repairs (wal_archive) stays in the data folder.

Exit codes

Syntax:

0   OK
1   error
2   damage found, or damage that could not be repaired
3   the database needs a newer KDB (nothing was changed)

Every kdb command ends with an exit code. Scripts use it to know if the command worked.

CodeMeaningExamples
0OKThe query ran. The backup was made. No damage found.
1ErrorWrong SQL. A duplicate key. The database is open in another program. Wrong arguments.
2Damagekdb check found damage. A data file failed its checksum. A repair could not fix everything.
3Needs a newer KDBA newer KDB wrote the database. It is not damaged: open it with that KDB (versions).
  • In PowerShell the exit code is in $LASTEXITCODE. In bash and zsh it is in $?. Read it right after the kdb command.
  • $ErrorActionPreference = "Stop" does not stop a PowerShell script when kdb fails. Check $LASTEXITCODE yourself.
  • Error messages go to the error output (stderr) and start with error:.
  • kdb shell ends with the exit code of the last statement or dot command.

Command line: 0 for a good query, 1 for a wrong table name (sample data: sample)

kdb sql market "SELECT count(*) AS n FROM brokers"
kdb sql market "SELECT count(*) FROM brokerz"

# In a script (not run here)
kdb check D:\kdb\market | Out-Null
switch ($LASTEXITCODE) {
  0 { "check: OK" }
  2 { "check: DAMAGE FOUND - run kdb repair" }
  3 { "check: this database needs a newer KDB - do not repair it" }
  default { "check: could not run (exit code $LASTEXITCODE)" }
}

How options are read

Syntax:

kdb <command> <arguments> [--option value] [--flag]

Options can come before or after the other arguments. Some options take a value (--format csv), some do not (--hard-links).

OptionValueUsed by
--data-dirfoldersql, shell, serve, info, check, repair, backup, user
--backupsfoldersql, shell, serve, repair
--memorymegabytessql, shell, serve

--statement-timeout, --max-result-memory, --max-groups, --max-queries-per-user, --safe-updates, --read-only, --trash-days, --audit, --audit-keep-days, --activity-log-sizesee protectionserve (--trash-days also sql, shell)

  • Notes: an option a command does not know is ignored without a message. Check the spelling: --hard-link (without s) makes a normal backup.
  • An option that takes a value always takes the next word, even when that word starts with --. So --token --port 9901 sets the token to --port.
  • A word that is not an option counts as an argument. kdb sql market "SELECT 1" --formt csv has one argument too many (csv), so it prints the usage line.
  • Text in arguments may use any language: kdb sql market "INSERT ... 'नेपाल'" works on Windows too.
