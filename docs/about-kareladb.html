KarelaDB (KARELA DataBase) is a small, general-purpose SQL database written in C++17. It runs as one program with no other software needed, and it keeps your data safe from crashes, power cuts and disk damage.

Created byAmrit Shrestha

Why the name changed

KarelaDB was called KDB until 2026-10-22. There is an older, well-known time-series database called kdb+ (with its language q) by KX Systems, and the two names were easy to mix up. KarelaDB has nothing to do with kdb+: its language is ordinary SQL. So the product took its full name, KARELA DataBase, written as KarelaDB.

Nothing changes for your data, and the old names keep working:

WhatNew nameThe old name still works?
The programkareladb (kareladb.exe on Windows)yes: kdb (kdb.exe) is the same program
Settings in the environmentKARELADB_TOKEN, KARELADB_DATA_DIR, ...yes: every KDB_* name is still read
The settings filekareladb.confyes: kdb.conf is read when there is no kareladb.conf
The Docker image and containerkareladba new image is named kareladb; start it on the same data folder and kdb_wal volume and it opens the same databases
The Claude skillkareladb (and kareladb-geometry)it still answers to "kdb", KDB_TOKEN and "port 9900"

If you installed the skill before the rename: after kareladb skill install, delete the old folder ~/.claude/skills/kdb (and its token file), so the assistant does not keep an old copy next to the new one. See the Claude skill.

What does not change at all: your data folders and files (kdb_data, the .kdb files, the log), the Docker volume kdb_wal, the ports 9900 and 8832, the HTTP routes and headers (X-KDB-...), the JSON fields, the metric names (kdb_...) and the SQL settings (kdb.pg_compat, ...). A database written before the rename opens as it is; nothing needs to be copied or converted.

One program, three doors

kareladb serve starts one server. You reach the same databases three ways:

DoorPortFor
Web console9900a browser: run SQL, see tables and charts, dashboards, settings
HTTP API9900any language or script: send SQL, get JSON back
PostgreSQL protocol8832psql, PostgreSQL drivers and apps written for PostgreSQL

Diagram: Three kinds of client, a web browser, apps and scripts, and PostgreSQL tools, reach the one kareladb program on ports 9900, 9900 and 8832. Inside the program the SQL engine sits on top of the storage engine.

Every door reaches the same SQL engine and the same data. The web console, the help and the Claude skill are plain folders next to the program.

  • A database is a folder. One server can hold many databases.
  • KarelaDB is one server on one machine. It is not a cluster that spreads data over many machines.
  • Nothing else is built into the program. The web console, the help and the Claude skill are the folders web/, help/ and skill/ next to kareladb, so a new console or help needs no new program. See where kareladb finds them.
  • You can also run it in Docker: the image (about 44 MB) holds the program and those three folders. See install-packages.

What you can use KarelaDB for

KarelaDB is not tied to one market or one kind of data. It holds time-series tables (rows that arrive in time order) and ordinary relational tables (rows linked by keys), and one query may use both.

How your data is kept safe

ProtectionWhat it does for you
Checksum on every blockEvery file is split into blocks, and each block has a CRC32C checksum. If one bit changes on the disk, KarelaDB finds it and knows which block is bad.
Write-ahead logEvery change is written to the log and saved to disk before KarelaDB says "committed". After a crash the log is played again, so no committed change is lost.
Copy-on-write filesA data file is never changed after it is written. KarelaDB writes a new version and then switches to it, so a crash never leaves a half-changed file.
Two manifest copiesThe list of current files is kept twice. KarelaDB always writes over the older copy, so one good copy is always left.
Repair ladderA damaged file is repaired from an older version first, then from a backup. If both fail, only that file is marked damaged and the rest still works.
Verified backupsAfter a backup, KarelaDB reads every file of it again. A backup that is not finished or not correct is never used.
Point-in-time restoreRestore a backup and replay the log up to an exact time, for example just before a bad import.

With --sync-commits batch (a disk flush every 10 ms, the faster setting) a power cut can lose writes from the last moments that were already confirmed. --sync-commits always flushes on every commit and loses nothing. See backup-and-safety and protection.
