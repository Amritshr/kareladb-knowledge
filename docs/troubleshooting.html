Troubleshooting a running server

What to look at, and what to change, when the server is slow, readers wait, memory or disk grows, the start is slow, a timer or a backup does not run, or data must come back.

  • Category: Backup, check, repair, restore
  • Keywords: troubleshooting, runbook, production problem, incident, server slow, slow server, slow queries, readers wait, reads wait, busy, table is busy, 55P03, 40001, lock timeout, memory high, out of memory, memory full, disk full, disk growing, disk space, trash, keep_versions, last shutdown: not clean, slow start, start-up slow, log replay, timer not running, timer did not run, backup failed, restore, what to do, symptom
  • See also: Monitor panel (memory, processor, caches), Health, info, check and backup over HTTP (metrics), Health, info, check and backup over HTTP (slow-queries), Transactions (lock-timeout), kareladb serve (memory-limit), Databases and the data folder (purge-trash), Timers, Backups on a schedule, Backup, check, repair and restore (after-damage)

Each part below is one symptom: what you see, where to check, and the fix. Start with the console's Monitor: it shows memory, the statements running now and the slow statements on one page.

The checks use three routes. Send the token as for any route: Authorization: Bearer <token>.

RouteShows
GET /api/statsmemory, running statements, waits, snapshot reads, databases that are still opening
GET /metricsthe same counters for Prometheus or Grafana
GET /api/slow-queriesthe statements that took longer than --slow-query-ms (1 second unless set)

The server is slow

CheckWhat it tells you
Monitor, Statements running nowone long statement that holds everything up. Cancel stops it.
GET /api/slow-queries?limit=20which statements are slow, who sent them, how many rows they gave
kdb_slow_statements_total in /metricswhether slow statements are new or have always been there
kdb_gate_waits_total{mode}, kdb_gate_wait_seconds_total{mode}time spent waiting for a lock, not working: see readers wait
kdb_partition_loads_total rising fastdata is read from disk again and again: --memory is too small for what is queried
EXPLAIN <the slow query>whether the query reads every partition (scan table t (120 of 120 partitions ...))
  • Fix: give a time range to queries of big time-series tables, add an index for lookups by one column, and see performance tips. Stop a runaway statement with Cancel, and limit them with --statement-timeout (protection).

Readers wait for a writer

A SELECT that is quick at night takes seconds by day, while a load, a trigger or a long CALL writes the same table.

CheckWhat it tells you
The start-up lines, readers ...whether reader yield is on
kdb_gate_wait_seconds_total{mode="read"}how long readers waited in total
snapshot_reads in /api/statswhether snapshot reads are on and used
  • Fix:
    • Keep reader yield on (--reader-yield on, KARELADB_READER_YIELD=on; on unless set). Readers then get in between the writer's statements.
    • Turn on snapshot reads (--snapshot-reads on, KARELADB_SNAPSHOT_READS=on) so readers do not wait even for one long statement, also on tables with an index of up to 1,000,000 rows (--snapshot-index-rows).
    • Split one huge statement (INSERT ... SELECT of millions of rows) into smaller ones: readers can only get in between statements.

Errors 55P03 and 40001: the table is busy

table 'x' is busy: another transaction has held it for N ms means a writer waited the lock timeout (5 seconds unless set) for another writer of the same table. Nothing of the statement was done.

CodeWhenFix
55P03 (HTTP 503)a statement outside BEGIN ... COMMITsend it again
40001 (HTTP 503)inside BEGIN ... COMMITROLLBACK and run the whole transaction again; drivers retry this code by themselves
40P01two transactions that would wait for each otherrun it again
CheckWhat it tells you
Monitor, Statements running nowthe transaction that holds the table, and for how long
idle_in_transaction_session_timeouta client that sent BEGIN and then nothing keeps the table until it is rolled back (30 s unless set, see idle transactions)
  • Fix: keep transactions short. For many small writers of one table that should queue instead of failing, raise the wait for them: SET lock_timeout = '20s' in the session, X-KDB-Lock-Timeout: 20s on one request, or --lock-timeout for the server.

Example: Let this session wait longer for a busy table, then go back to the server's wait

SET lock_timeout = '20s';
SET lock_timeout = DEFAULT;

Result:

SET lock_timeout = '20s'

lock_timeout is 20 s for this session

SET lock_timeout = 'DEFAULT'

lock_timeout is the server's default again

Memory is high

CheckWhat it tells you
Monitor, Memory in RAM and Most it ever heldwhat the process holds now, and at its peak
kdb_memory_bytes{kind} in /metricswhich part is big: table_data, key_maps, indexes, pending, result_cache, allocator ...
kdb_memory_level0 green, 1 yellow, 2 red: near the memory limit
errors memory full: ... (HTTP 503)the limit stopped new work instead of the process being killed
SettingWhat it limits
--memory <MB> (KARELADB_MEMORY)table data kept loaded. Data over it is read from disk again.
--memory-limit <size> (KARELADB_MEMORY_LIMIT)everything together. Keep --memory at about half of it.
--max-result-memoryone query's result (protection)
GLIBC_TUNABLES=glibc.malloc.arena_max=8:glibc.malloc.trim_threshold=67108864Linux and Docker: how much freed memory the C library keeps; without it the process can hold far more than it uses
  • Fix: allocator big: set GLIBC_TUNABLES as above (see Docker). table_data big: lower --memory. A query that needs much memory: add a time range or a LIMIT. A transaction that fails with transaction too big for memory: split it.

The start is slow, or says "last shutdown: not clean"

last shutdown: not clean (crash or kill) in the start-up lines means the server was killed, not stopped. That is not damage: KarelaDB replays the log, and every confirmed change comes back. Replaying a long log takes time.

CheckWhat it tells you
the recovery start-up lineclean or not, and how many log records were replayed
opening_databases in /api/statsdatabases still opening, and for how long
  • Fix: stop the server so it can finish: Ctrl+C, docker stop, or a service stop. A Docker container needs --stop-timeout 60 when it is created; without it, Docker Desktop kills it about 1 second after asking it to stop, and every start replays the log (Docker, stopping). Do not use docker rm -f or docker kill on a running server.

A timer does not run

CheckWhat it tells you
GET /api/timersenabled, next_run_ms (0 = off), last_run_ms, last_ok, last_error
kdb_timer_failures_total, kdb_timer_late_seconds_maxfailed runs, and how late runs started
CauseFix
the timer is offturn it on (Timers page, or POST /api/timers/<name>/enable)
it runs at the wrong hourtimes are the server's clock; a container runs on UTC. Set --timezone Asia/Kathmandu
last_error says whyfix the SQL, or the rights of the user who saved it last (it runs with them)
the run before is still goinga run is skipped when the one before has not finished. Make the SQL faster; a run stops after 10 minutes
its database was droppeddelete the timer

A backup failed

CheckWhat it tells you
backup_schedule in GET /api/infolast_run_ok, warning (the last good backup of 'x' is N hours old), and per database error
backup_command in /api/infothe copy command's exit code and the end of what it printed
kareladb backups <dir>the backups there, and whether each is whole
CauseFix
disk fullfree space, or keep fewer backups (backup_keep_daily, backup_keep_weekly) (when the disk is full)
the folder is not there, or not writableinside Docker it must be under a mounted volume
the copy command failedrun the command by hand with the same folder

Then run one backup now to see that it works: POST /api/backup, or Back up now in the console.

Getting data back

What happenedSteps
a table was droppedUNDROP TABLE t within --trash-days (the trash)
a bad UPDATE or DELETErestore while the server runs: POST /api/restore with "until" one second before the mistake into a new name, check it, then POST /api/databases/swap
damaged files (failed its checksum, DAMAGED)stop, copy the folder, kareladb check, kareladb repair --backups <dir> (after damage)
the whole folder is lostkareladb restore <newest backup> <new folder>, kareladb check <new folder>, then start the server on it (kareladb restore)

Command line: Check a database, then repair it from the backups (sample data: sample)

kareladb check market
kareladb repair market --backups backups

Output:

> kareladb check market

checked 14 files (76.1 KB) and 1 log segments
OK: no damage found

> kareladb repair market --backups backups

manifest copy: a, last shutdown: clean
replayed 0 transactions after LSN 30, last LSN 30

Nothing to repair.
