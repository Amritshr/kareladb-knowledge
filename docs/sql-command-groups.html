SQL command groups: DDL, DML, DCL, TCL, DQL

The five groups of SQL statements, every KarelaDB statement in its group, and the role each group needs.

  • Category: Getting started
  • Keywords: DDL, DML, DCL, TCL, DQL, data definition language, data manipulation language, data control language, transaction control language, data query language, command groups, statement types, kinds of statements, sublanguage, which role do I need, TRUNCATE, SAVEPOINT
  • See also: SQL basics, CREATE TABLE, ALTER, RENAME and DROP TABLE, Views, Indexes, INSERT, UPDATE and DELETE, Users and roles, Transactions, SELECT, SHOW TABLES, COLUMNS, CREATE TABLE

SQL statements are sorted into five groups by what they do. The group tells you three things at once: what the statement changes, which role a user needs for it, and whether it can go inside BEGIN ... COMMIT.

GroupNameWhat it doesMain statementsRole needed
DDLData Definition Languagemakes, changes and removes objects: tables, views, indexes, functions, procedures, triggersCREATE, ALTER, DROP, RENAMEadmin
DMLData Manipulation Languagechanges the rows inside tablesINSERT, UPDATE, DELETE, CALLwrite
DCLData Control Languagesays who may do whatCREATE USER, GRANT, REVOKEadmin as the user's own ROLE
TCLTransaction Control Languagegroups changes so they are saved together or not at allBEGIN, COMMIT, ROLLBACKread
DQLData Query Languagereads rows and never changes anythingSELECT, EXPLAIN, SHOWread
  • Roles are checked only by kareladb serve (HTTP, web console and the PostgreSQL port). kareladb sql and kareladb shell open the files directly and may run everything.
  • Some books put SELECT into DML. KarelaDB's help keeps it apart as DQL, because a read needs only the read role.
  • The web console lists what DDL made: open the Objects list on the left (see web console).

DDL: Data Definition Language

DDL statements build the shape of a database. They change objects, not rows (except DROP, which removes the rows with the table).

ObjectMakeChangeRemoveHelp
tableCREATE TABLEALTER TABLE, RENAME TABLEDROP TABLE, then UNDROP TABLE to bring it backcreate-table, alter-table, trash
viewCREATE VIEW, CREATE CACHED VIEWdrop and create againDROP VIEWviews
materialized viewCREATE MATERIALIZED VIEWALTER TABLE ... SET TTL; otherwise drop and create againDROP MATERIALIZED VIEWviews
indexCREATE INDEX, CREATE UNIQUE INDEX, CREATE FULLTEXT INDEX-DROP INDEXindexes
saved functionCREATE FUNCTIONCREATE OR REPLACE FUNCTIONDROP FUNCTIONsaved-functions
stored procedureCREATE PROCEDURECREATE OR REPLACE PROCEDUREDROP PROCEDUREprocedures
triggerCREATE TRIGGERALTER TRIGGER ... ENABLE / DISABLEDROP TRIGGERtriggers
sequenceCREATE SEQUENCEALTER SEQUENCEDROP SEQUENCEfunctions-postgres
ENUM typeCREATE TYPE ... AS ENUMALTER TYPE ... ADD VALUEDROP TYPEcolumn-types
trading calendarCREATE CALENDARALTER CALENDAR ... ADD HOLIDAY / ADD ERA / ...DROP CALENDARcalendars
databaseCREATE DATABASEALTER DATABASEDROP DATABASEdatabases
  • Role: admin. Databases need admin as the user's own ROLE.
  • Notes:
    • Each DDL statement is saved on its own, at once. Most of them can not go inside BEGIN ... COMMIT (see what is not allowed inside a transaction).
    • Look at what DDL made with SHOW TABLES, SHOW COLUMNS FROM t, SHOW CREATE TABLE t, SHOW VIEWS, SHOW INDEXES, SHOW FUNCTIONS, SHOW PROCEDURES and SHOW TRIGGERS (see show-tables).
    • TRUNCATE TABLE t empties a table and keeps it (see UPDATE and DELETE). PostgreSQL counts it as DDL.

CREATE VIEW watchlist_names AS
SELECT w.symbol, s.name, w.target FROM watchlist w JOIN securities s ON s.symbol = w.symbol;

DML: Data Manipulation Language

DML statements change the rows of tables. The table itself stays as it is.

StatementWhat it doesHelp
INSERT INTO ... VALUESadds rowsinsert
INSERT OR REPLACE, INSERT OR IGNORE, ON CONFLICTadds rows, or replaces / keeps the row with the same keyinsert
INSERT INTO ... SELECTadds the rows a query givesinsert
UPDATE ... SET ... WHEREchanges rowsupdate-delete
DELETE FROM ... WHEREremoves rowsupdate-delete
... RETURNINGshows the rows that were added, changed or removedupdate-delete
CALL name(...)runs a stored procedure, which changes rowsprocedures
  • Role: write.
  • Notes:
    • Each statement is all or nothing: an INSERT of 5000 rows with one bad row saves no row.
    • To make many DML statements succeed or fail together, put them inside BEGIN ... COMMIT (TCL).
    • Triggers run by themselves after (or before) DML on their table.
    • A view has no rows of its own: DML on a view is refused. Change the table the view reads.

Example: DML: add, change and remove rows (sample data: sample)

Setup:

CREATE TABLE watchlist (symbol STRING PRIMARY KEY, note STRING, target DOUBLE);
INSERT INTO watchlist VALUES ('CITY', 'bank', 520), ('VOLT', 'hydro', 250);
UPDATE watchlist SET target = 540 WHERE symbol = 'CITY';
DELETE FROM watchlist WHERE symbol = 'VOLT' RETURNING symbol, note;
SELECT * FROM watchlist;

DCL: Data Control Language

DCL statements decide who may connect and what each user may do.

StatementWhat it doesHelp
CREATE USER name PASSWORD '...' ROLE ...adds a user with a role for every databaseusers-and-roles
ALTER USERchanges a password or a roleusers-and-roles
DROP USERremoves a userusers-and-roles
GRANT role ON DATABASE db TO namegives a role on one databaseusers-and-roles
GRANT ... ON TABLEgives rights on one tabletable-rights
REVOKE ... FROM nametakes a grant awayusers-and-roles
SHOW USERSlists users, roles and grantsusers-and-roles

The roles, from least to most: none < read < write < admin. Each role may do everything of the roles before it.

  • Role: admin as the user's own ROLE (a GRANT of admin on one database is not enough), because users belong to the whole server. Changing your own password needs no role.
  • Notes:
    • The first user must have ROLE admin. From then on, kareladb serve asks everyone to log in.
    • Users are kept in the _system database, not in the database you are using.
    • Give each program only what it needs: an app's backend write on its own database, a report script read.

Example: DCL: an admin, a read-only report user, and an app that may write one database (sample data: sample)

Setup:

CREATE USER admin WITH PASSWORD 'Long-Admin-Passw0rd' ROLE admin;
CREATE USER report WITH PASSWORD 'Reports-only-secret-7' ROLE read;
CREATE USER shop_app WITH PASSWORD 'Another-long-secret-42' ROLE none;
GRANT write ON DATABASE demo TO shop_app;
SHOW USERS;

TCL: Transaction Control Language

TCL statements group DML into one transaction: KarelaDB saves all of its changes together, or none of them.

StatementWhat it doesHelp
BEGIN (also BEGIN TRANSACTION, BEGIN WORK)starts a transactiontransactions
COMMITsaves every change since BEGIN, in one writetransactions
ROLLBACKthrows away every change since BEGINtransactions
SELECT ... FOR UPDATEreads rows that no other session may change before you COMMITtransactions
  • Role: read to start and end one. The statements inside still need their own role (write for DML).
  • Notes:
    • Without BEGIN, every statement is its own small transaction and is saved at once.
    • When a statement inside the transaction fails, KarelaDB undoes the whole transaction.
    • SAVEPOINT, ROLLBACK TO SAVEPOINT and RELEASE SAVEPOINT undo part of a transaction (savepoints).
    • One writer at a time: while a transaction changes rows, other writers wait (see one writer at a time).

Example: TCL: a transfer that is saved, and a mistake that is undone (sample data: sample)

Setup:

CREATE TABLE accounts (id INT PRIMARY KEY, owner STRING NOT NULL, balance DECIMAL(2) NOT NULL);
INSERT INTO accounts VALUES (1, 'Ram', 1000), (2, 'Sita', 0);
BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
UPDATE accounts SET balance = balance + 300 WHERE id = 2;
COMMIT;

BEGIN;
DELETE FROM accounts;
ROLLBACK;

SELECT * FROM accounts ORDER BY id;

DQL: Data Query Language

DQL statements read. They never change a row or an object, so they are safe to run at any time.

StatementWhat it doesHelp
SELECTreads rows: WHERE, JOIN, GROUP BY, ORDER BY, LIMITselect
SELECT ... SAMPLE BY, LATEST ONtime-series candles and the newest row per keysample-by, latest-on
WITH ... SELECTa query with named partsunion-subqueries
EXPLAIN SELECT ...shows how KarelaDB will run a query, without running itexplain
SHOW TABLES, SHOW VIEWS, SHOW INDEXES, ...lists the objects of a databaseshow-tables
DECLARE, FETCH, CLOSEreads a big result a part at a timecursors
  • Role: read.
  • Notes:
    • Selecting from a view is DQL too: the view's query runs, and nothing is changed.
    • SELECT ... FOR UPDATE is the one read that waits for writers; it belongs with TCL.

Example: DQL: a report, a query plan and a list of objects (sample data: sample)

FROM trade_log GROUP BY symbol ORDER BY trades DESC, symbol LIMIT 3;

Which group is my statement?

Starts withGroup
CREATE, ALTER, DROP, RENAME, UNDROP (tables, views, indexes, functions, procedures, triggers, sequences, databases)DDL
INSERT, UPDATE, DELETE, CALLDML
CREATE USER, ALTER USER, DROP USER, GRANT, REVOKEDCL
BEGIN, COMMIT, ROLLBACKTCL
SELECT, WITH, EXPLAIN, SHOW, DECLARE, FETCH, CLOSEDQL

Other statements belong to looking after the database, not to one of the five groups: BACKUP DATABASE, CHECK TABLE, CHECKPOINT (see backup and safety) and USE (see databases).
