This page lists what was added to KarelaDB from 2026-09-12 to 2026-09-24. Each line says what changed, the number measured before and after (where there is one), and where to read more.

  • Numbers are medians on one PC (Intel i9-14900HX, 32 GB). The reports say how each was measured.
  • "A -> B" means before -> after, on the same machine in the same minutes.
  • A switch like KARELADB_NO_ZONE_MAPS=1 turns a new speed-up off. It is there so an answer can be checked against the old path, not for normal use.

2026-10-22: automatic failover with a cluster of two servers and a witness

What changedMeasuredRead more
kareladb serve --node-id a --cluster-peers a=...,b=...,w=... and kareladb witness: three voters elect a leader; the leader takes writes, the other data node copies it. When the leader dies, the other is elected and takes over by itself.kill -9 of the leader: the other data node led after 4.3 to 4.6 s, 3 rounds, the old leader back as a follower each time with every row (three processes in WSL, ASan build)cluster
A leader that no longer hears a majority stops writing (25006) within its 3 s lease, before anyone can be elected (4 s at the soonest), and a follower never applies the log of a leader from an older term.-fencing

2026-10-18: a join to a small table runs as a key lookup; a day's grouping in fewer steps

What changedMeasured (10M floorsheet trades, 2 CPUs, 1.5 GB memory budget, WSL with an emulated 2-CPU quota)Read more
A grouped view joined to a total of itself over some of its keys (df d JOIN (SELECT time, symbol, sum(buy_qty) AS tot FROM df GROUP BY time, symbol) t ON d.time = t.time AND d.symbol = t.symbol, each broker beside the symbol-day's total) makes the totals inside the view's own grouping: no row of the view is joined. An INNER JOIN on all of t's keys, t's aggregates sum / min / max of the view's sum / count / min / max outputs, a WHERE that narrows by those keys and by aggregates only. EXPLAIN says "to its own totals"; KARELADB_NO_SELF_JOIN_TOTALS=1 turns it off.OTM filter, one day: 7.6 -> 6.3 ms (side by side on a busy host)views
A HAVING that reads only aggregates (a CASE flag, comparisons, AND / OR / NOT, IN, BETWEEN) is worked out column-wise over all the groups at once, with the same NULL rules, instead of one group at a time. An average, a first/last, a DECIMAL sum or whole-number arithmetic in the test still goes group by group; KARELADB_NO_VECTOR_HAVING=1 turns it off.OTM flag test over a day's 10,000 groups: 3.9 -> 1.4 ms (the step alone)HAVING
A GROUP BY over a view joined to a small table whose columns are only group keys (df d JOIN sector s ON d.symbol = s.symbol GROUP BY d.time, d.broker, s.sector) runs the join as a lookup of the key inside the view's own grouping: no row of the view is made. Only an INNER JOIN on one column, a table of up to 65,536 rows that holds each key once, and columns of texts or whole numbers without NULLs. EXPLAIN says "run as a lookup of".broker-sector, one day: 4.9 -> 1.1 ms; over a year: 31 -> 16 msviews
A GROUP BY of two to four keys (time, symbol, broker) keeps them in one 64-bit number, each key in the bits its saved stats call for, so the merge compares numbers and not 48-byte keys.daily filter, one day: 3.6 -> 2.6 ms; OTM filter, one day: 6.0 -> 5.4 msGROUP BY
The small steps around a day's grouping cost less: the zero and one columns of a UNION ALL part are kept across queries instead of being made as long as the partition each time, the merge tables are sized once from the pieces, and with few groups the steps after the scan run on one thread instead of a pass over the pool each. KARELADB_FLAT_TRACE=1 prints where a grouping's time goes.(in the numbers above)GROUP BY

Faster loads

Big loads go through the fast columnar path in more cases, and a trigger on one table no longer slows the others.

What changedMeasuredRead more
Line protocol in one pass (2026-10-06). A line shaped like the one before it is read in one pass, and its values go straight into the table columns; a line that is different in any way is read as before, with the same errors.1 million trades lines in 100,000-line batches, 2 cores: 1.55M -> 2.2M rows/s, half the server CPU; 2 million candles 1.7M -> 2.4M rows/sline protocol
Tables without a DEDUP KEY are written as runs. A trade list, where two trades in one second are both real, now takes the same fast path as a candle table.814,535 real trades, 20,000 rows a request: 438k -> 918k rows/s; QuestDB 678k rows/s on the same PC (KarelaDB 35% faster, was 36% slower)line protocol, report

Deferred triggers. CREATE TRIGGER ... AFTER INSERT ON t DEFERRED runs the trigger body after the load returns, as a background job.a 20,000-row write into a table with a heavy trigger: 103 -> 9 ms once the trigger is deferredtriggers

Search

Searches of 200,000 news articles now beat PostgreSQL 18 with a GIN index on every measured query but one, where the two tie.

The one tie is a word plus a symbol and a month (0.54 vs 0.48 ms). The articles hold 378 MB of text.
