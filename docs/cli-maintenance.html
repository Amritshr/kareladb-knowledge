kareladb info, check, repair, dump-file

Look inside a database, find damage, repair it, and check one file.

  • Category: Command line
  • Keywords: damage, damaged, corruption, checksum, failed its checksum, repair ladder, scrub, manifest, manifest keys, stale keys, LSN, log position, last shutdown, not clean, --accept-log-loss, log loss, torn tail, DAMAGED, PROBLEM, NEEDS REPAIR, maintenance
  • See also: Backup, check, repair and restore, Backup, check, repair and restore (after-damage), How KarelaDB stores data, The kareladb program (exit-codes)

These commands look after a database folder. kareladb info, kareladb check and kareladb dump-file only read. kareladb repair changes the database.

All of them need the database closed: stop kareladb serve, kareladb shell and other programs that use it first. While a server runs, use its console (Check now) or POST /api/check instead.

What to do after damage, step by step: after damage. How the files look: data formats.

kareladb info

Syntax:

kareladb info <db> [--data-dir <folder>]

Shows what the manifest (the list of current files) says: the files, their versions, sizes and log positions. It does not read the files themselves. To find new damage, use kareladb check.

Line or columnMeaning
databaseThe folder that was opened
manifestcopy a or copy b: which of the two manifest copies is newest, and its sequence (how often it was saved). A note: line under it says when one copy could not be used.
last shutdownclean, or not clean (running now, crashed or killed)
log position N (saved in files up to M)N = number (LSN) of the last change in the log. M = every change up to M is in the data files.
newest changeTime of the last change, in the local time of this computer
featuresThe stored-format features the database uses, or no list yet for a database of an older KarelaDB (versions)
manifest keysHow many extra entries the manifest holds (partition summaries and row counts of files). (N of files that are gone: ...) counts stale ones, left by a DROP TABLE of an older build; they are removed the next time the database is opened for writing. Harmless.
FILEcatalog = the list of tables. t/4/2026-09 = table number 4, partition 2026-09. all = a table without partitions.
VERSIONVersion of the file. A change writes a new version.
LSNThe file holds every change up to this log position
STATUSok, or DAMAGED: <reason> when KarelaDB marked the file as damaged
last lineN files, <size>, M marked damaged
  • Exit code: 0; 2 when a file is marked damaged; 1 when the folder has no manifest (not a database).
  • LSN = log sequence number: every change in the log gets the next number.
  • last shutdown: not clean (running now, ...) is normal while a program has the database open.

kareladb check

Syntax:

kareladb check <db> [--data-dir <folder>] [--no-audit-chain]

Reads every block of every data file and every record of the log, and checks each checksum. It reports damage and changes nothing (it opens the database read-only).

  • Exit code: 0 = no damage. 2 = damage found. 3 = the database was written by a newer KarelaDB: not damage, do not repair it (versions). 1 = it could not run (the folder does not exist, or the database is open in another program).
  • Output lines: OK: no damage found, or one line per problem: DAMAGED: (a file that could not be loaded), NEEDS REPAIR: (a problem kareladb repair can fix), PROBLEM: (a bad block, a bad log record).
  • Audit chain: when the files are sound and the database has an audit log, it then checks the hash chain of _audit_log: audit chain: N row(s) checked ..., or TAMPERED: for a row that was changed or removed outside KarelaDB (exit code 2). This opens the database read-only and replays its log in memory; --no-audit-chain skips it.
  • Run it every day, right after the backup. It is also the SQL CHECK TABLE and the shell's .check.
  • Time: it reads everything, so a big database takes a while (about as long as copying it).

Command line: A healthy database (sample data: sample)

kareladb check market

Output:

checked 14 files (76.1 KB) and 1 log segments
OK: no damage found

kareladb repair

Syntax:

kareladb repair <db> [--backups <dir>] [--accept-log-loss] [--data-dir <folder>]

Opens the database and fixes damaged files with the repair ladder. Then it reads everything again and says what is still damaged.

OptionMeaningDefault
--backups <dir>Backups to take good copies of files and log records from. For a database name in the data folder, KarelaDB looks in <dir>/<name>.only old versions on disk
--accept-log-lossLast choice: when needed log records are damaged, cut the log there and open anyway. The changes in the damaged part are lost.refuse to open
--data-dir <folder>The data folderKARELADB_DATA_DIR

The repair ladder for one damaged data file. KarelaDB tries each rung, top to bottom:

RungKarelaDB triesThen
1The previous version of the file (KarelaDB keeps 2)Replays the log from that version, so no change is lost
2The same file from a backup (--backups), newest backup firstCopies it back and replays the log from the backup's position, so changes made after the backup come back too
3Nothing workedMarks only this file as DAMAGED. The rest of the database still works.
  • Exit code: 0 = Repaired. or Nothing to repair. 2 = Some damage could not be repaired. 3 = the database needs a newer KarelaDB; nothing was repaired or changed. 1 = it could not run (for example the database is open in another program).
  • Before a repair, copy the whole damaged folder to a safe place. Then nothing you try can make it worse.
  • Only backups of the same database are used. A backup of another database, or of a history that a restore left behind, is never used.
  • A log that is only damaged at the very end (a write that a crash cut in half) needs no repair: it is cut away when the database opens, and the output says dropped an unfinished write at the end of the log.
  • Damaged log records that are still needed: KarelaDB refuses to open and names the log file. Try, in this order: kareladb repair <db> --backups <dir> (copies the good bytes from a backup), then kareladb restore with --logs-from, and only then --accept-log-loss.
  • Notes: kareladb repair on a folder that does not exist makes a new, empty database there and says Nothing to repair. Check the path.

kareladb dump-file

Syntax:

kareladb dump-file <file.kdb>

Shows the 64-byte header of one KarelaDB file and checks the checksum of every block. For experts: use it to look at one file that kareladb check named.

LineMeaning
typedata file, manifest, backup manifest or WAL segment (a log file)
versionFile format version (1)
dataSize of the data in the file
block sizeThe data is cut into blocks of this size (65536 bytes); each block has a CRC32C checksum
LSNThe file holds every change up to this log position
idFor a data file: the table number. For a manifest: its sequence number.
createdWhen the file was written (local time)
blocks, digestNumber of blocks, and one checksum over the header and all block checksums
last lineOK: all blocks match their checksums, or DAMAGED block N for each bad block
  • Exit code: 0 = all blocks are good. 2 = a damaged block, or a header that is not a KarelaDB header. 1 = the file cannot be opened.
  • For a log file (wal/*.log) it shows only the header.
  • Data files are in files/t/<table number>/<partition>.v<version>.kdb. kareladb info lists them.
