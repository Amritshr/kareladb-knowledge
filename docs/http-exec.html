Run SQL over HTTP (/exec, /exp)

Run SQL with GET or POST /exec and get JSON, or download the rows of a SELECT as CSV with /exp.

  • Category: HTTP API
  • Keywords: exec, /exec, exp, /exp, query, limit, compat, compat, cache, result cache, benchmark, SET result_cache, cache_now_ms, result_cache_now_ms, truncated, dataset, columns, count, timings, rows_affected, QuestDB, CSV export, download CSV, filename, Content-Disposition, form field, many statements, results array, error line column, --data-binary, --data-urlencode, NaN, nan, Infinity, timestamp as text, epoch milliseconds, statement failed, partial success, atomic, atomic, X-KDB-Atomic, all or nothing, rolled_back, saved, sqlstate, constraint, error code
  • See also: HTTP API overview, Sessions and cursors over HTTP, Databases over HTTP (/api/databases), SELECT, Transactions, How KarelaDB stores data

/exec runs SQL and answers with JSON. /exp runs a SELECT and answers with a CSV file (text with one row per line and commas between the values, which Excel opens).

  • GET only runs SQL that reads. POST runs any SQL.
  • Each request uses one database: db=<name> or the header X-KDB-Database (choosing the database).
  • The answer looks like QuestDB's /exec, so QuestDB clients keep working (moving from QuestDB).

GET /exec

Syntax:

GET /exec?query=<SQL>[&db=<name>][&limit=N][&compat=0][&cache=0][&format=rows|columns][&nan=null|string][&session=<id>]

Runs SQL that only reads (SELECT, SHOW ..., EXPLAIN, CHECK TABLE, USE) and answers with JSON. SQL that changes data gets 405: use POST /exec.

ParameterWhereMeaningDefault
queryURLThe SQL. One or more statements, split by ;. Encode spaces and ' in the URL (curl -G --data-urlencode does it).required
dbURLThe database. The header X-KDB-Database: <name> does the same.the default database
limitURLMost rows each statement gives back. 0 or less means 1,000,000. QuestDB style limit=10,500 uses the second number.10,000
compatURLcompat=0 (or false) leaves out the copy of the last result at the top level.1
cacheURLcache=0 (or off, false) runs a SELECT fresh: it is not taken from the result cache and not kept there. Use it to time the engine in a benchmark. For a whole session: SET result_cache = off. A SELECT that must always be ready can be pinned.1
cache_now_msURLA SELECT with now() (or current_date) may be answered by a kept result up to this old, like 500 or 2s. Without it such a SELECT is never kept. For a whole session: SET result_cache_now_ms = 500.0
formatURLcolumns: every dataset as one array per column (format=columns)rows
nanURLstring: NaN, Infinity and -Infinity as the JSON strings "NaN", "Infinity", "-Infinity" instead of null (nan=string)null
sessionURLA session id from POST /session. The header X-KDB-Session: <id> does the same.none
If-None-MatchheaderThe ETag of an earlier answer: a 304 with no body while the rows are the same (ETag)none
Answer fieldMeaning
queryThe SQL you sent (only the first 4,096 bytes of a very long text)
results[]One object for each statement, in order
results[].statementThe statement, as KarelaDB wrote it back
results[].columns[]name and type of each column (LONG, DOUBLE, TIMESTAMP, ...)
results[].datasetThe rows. Each row is a list of values in column order.
results[].countNumber of rows in dataset
results[].truncatedtrue when there were more rows than limit
results[].rows_affectedRows changed by INSERT, UPDATE or DELETE
results[].messageA short message, like 1 row(s) inserted
results[].timingsparse_us and execute_us: microseconds (millionths of a second) to read and to run the statement
columns, dataset, countA copy of the last result at the top level, as QuestDB answers. Not there with compat=0.
timingsThe sum of the timings of all statements

How values look in dataset:

KarelaDB typeJSON value
INT, LONG, DOUBLE, ...a number: 512.4
a whole number bigger than 9,007,199,254,740,992 (2^53)text: "9007199254740993", so JavaScript does not lose digits
DECIMAL(s)text with exactly s places: "1500.25" (it stays exact)
TIMESTAMPUTC text: "2026-09-10T05:15:00.000Z"
DATEtext: "2026-09-10"
BOOLtrue or false
SYMBOL, STRINGtext
JSONthe JSON itself (an object or a list), not a text
NULL, and a number that is not real (like sqrt(-1))null
a DOUBLE that is NaN, Infinity or -Infinitynull, as QuestDB writes it; "NaN", "Infinity", "-Infinity" with nan=string
  • Times are text, not numbers: every TIMESTAMP, also min(time) and max(time), comes as text like "2026-09-10T05:15:00.000Z". In JavaScript Number(value) gives NaN; use Date.parse(value) (milliseconds). Or ask SQL for a number: CAST(time AS LONG) gives milliseconds since 1970-01-01 UTC, date_part('epoch', time) gives seconds.
  • Status codes: 200 OK; 304 the If-None-Match tag still fits; 400 bad SQL, no query, or a format that is not rows or columns; 401/403 login or role; 404 unknown database or session; 405 SQL that changes data; 408 the statement ran past the statement timeout; 500 server trouble (damaged file); 503 the database is busy with another transaction, or the server is stopping.
  • Notes: GET must only read because a link or picture on another web page can make your browser send a GET. limit cuts each statement's rows, so "truncated": true tells you more rows exist: use a bigger limit, GET /exp or a cursor.
  • 10,000 rows: without limit, /exec gives back at most 10,000 rows per statement, so a forgotten WHERE cannot send millions of rows to a browser. Ask for more with limit= (up to 1,000,000).

HTTP: No query

GET /exec

Response:

HTTP 400 (application/json)

{"error": "missing query: use /exec?query=<SQL> or POST the SQL as the body"}

With curl, let it encode the SQL (-G puts the data into the URL):

curl -s -G "http://127.0.0.1:9900/exec" --data-urlencode "query=SELECT symbol, close FROM ochl_day WHERE symbol = 'CITY' LIMIT 2" --data-urlencode "compat=0"
$q = [uri]::EscapeDataString("SELECT symbol, close FROM ochl_day WHERE symbol = 'CITY' LIMIT 2")
$r = Invoke-RestMethod "http://127.0.0.1:9900/exec?compat=0&query=$q"
$r.results[0].dataset | ForEach-Object { $_ -join " | " }

POST /exec

Syntax:

POST /exec[?db=<name>][&limit=N][&compat=0][&cache=0][&format=rows|columns][&nan=null|string][&session=<id>][&atomic=1]
body: the SQL text
   or a form (Content-Type: application/x-www-form-urlencoded) with the field query=<SQL>

Runs any SQL: INSERT, UPDATE, CREATE TABLE, CALL, BEGIN, many statements at once. The answer has the same fields as GET /exec.

ParameterWhereMeaningDefault
bodybodyThe SQL. Send it as plain text (Content-Type: text/plain; charset=utf-8), in UTF-8.required
queryform fieldThe SQL, when the body is a form. Without a query= field the whole body is the SQL.-
dbURL or form fieldThe database. Or the header X-KDB-Database.the default database
limitURL or form fieldMost rows per statement (as for GET)10,000
compatURL or form fieldcompat=0 leaves out the top-level copy1
cacheURLcache=0 skips the result cache (as for GET)1
formatURL or form fieldcolumns: one array per column (as for GET)rows
nanURLstring: NaN and the infinities as JSON strings (as for GET)null
sessionURL, form field or header X-KDB-SessionRun inside a session: BEGIN in one request, COMMIT in a later onenone
atomicURL, form field or header X-KDB-Atomic1: the whole body is one transaction, all or nothing (see atomic=1)0
Answer fieldMeaning
query, results[], columns, dataset, count, timingsas in GET /exec
error(only on an error) what went wrong
sqlstate(only on an error) the same five-character code the PostgreSQL port sends: 23505 duplicate key, 23503 foreign key, 42P01 unknown table, the code of a trigger's RAISE ... USING ERRCODE, ...
table, constraint, column_name(only on a 23505 or 23503 error) the table and constraint it was about, like users and users_email_key, and the column when the constraint has one
line, column(only on an error, when KarelaDB knows it) where in the text you sent. Counted in characters, from 1.
saved(only on an error) how many entries of results, from the first, are saved. The same with or without compat=0.
rolled_back(only on an error) true when a transaction was rolled back by the error: the entries after saved ran but are not saved
  • Status codes: 200 OK; 304 (as for GET); 400 bad SQL (syntax, unknown column, duplicate key, ...) or a damaged compressed body; 401/403 login or role; 404 unknown database or session; 408 statement timeout; 413 body over 64 MB (counted after unpacking); 500 server trouble; 503 database busy, the server is stopping, or the system was short of memory for a moment (send it again; a 500 that says applied in memory must not be sent again); 507 the disk is full (the write was not saved; it works again once space is freed).
  • Compressed body: a body sent with Content-Encoding: gzip or deflate is unpacked before it is read. Handy for a long INSERT script.
  • Many statements: they run one after the other. Each one is saved when it is done (unless you opened a transaction with BEGIN). When one statement fails:
WhatValue
HTTP statusnot 200: 400 for bad SQL, a table that already exists, a duplicate key, ...; the other codes above for other trouble
errorat the top level of the answer: what went wrong (with line and column when KarelaDB knows them)
resultsonly the statements that ran before the failed one. The failed statement is not in results.
savedhow many of results are saved. Without BEGIN in the body: all of them.
rolled_backtrue when the body had a BEGIN without COMMIT before the error (or atomic=1, or a session's open transaction): those statements were undone
statements after itdid not run
  • Check the status code or error first. A client that only reads results sees the statements that worked and can think a failed CREATE TABLE worked too.
  • Read saved, not the length of results, to know what is really in the database.
  • A syntax error in any statement is found before anything runs: status 400, results is empty, and nothing is saved, not even the statements before it.
  • Notes: curl --data sends the body labelled as a form; that still works, because a form without a query= field is taken as the SQL. Use --data-binary so curl does not change line breaks. To send a .sql file with text in any language (Nepali, Chinese, ...), send the file's bytes. A body can be up to 64 MB (a big batch of INSERTs); for fast loading also see the line protocol.

NaN and Infinity: nan=string

JSON has no numbers for NaN, Infinity and -Infinity. By default /exec writes them as null, as QuestDB's /exec does, so an old client reads them as it always did. A null there cannot be told from a real NULL, though: with ?nan=string they come as the strings "NaN", "Infinity" and "-Infinity" (the spelling PostgreSQL and JavaScript use; Number("NaN") is NaN).

Nothing to send: ETag and If-None-Match

Every /exec reply that carries a dataset names it in an ETag header - a checksum of the dataset's bytes, its size and its shape. A client that keeps the last answer sends the tag back:

POST /exec?compat=0
If-None-Match: "102625ff-1bcr"

SELECT time, close FROM ochl_day WHERE symbol = 'CITY' ORDER BY time

HTTP/1.1 304 Not Modified
  • While the data is the same the answer is a 304 with no body: a page that refreshes every few seconds costs the query, not the bytes.
  • The query still runs (or comes from the result cache); only the sending is saved.
  • The tag changes as soon as any row the query reads changes, because it is made from the answer itself; with the result cache on, a repeated query with the same tag is answered from memory.
  • The row and column shapes have different tags.

All or nothing: atomic=1

With atomic=1 (or the header X-KDB-Atomic: 1) the whole body runs as one transaction. When any statement fails, every statement of the body is rolled back.

CaseAnswer
all statements work200, the normal answer. Everything is saved together.
a statement failsnot 200, error, "saved": 0, "rolled_back": true. Nothing is saved.
the body has a statement that cannot run in a transaction400 before anything runs, "results": []
  • Allowed: SELECT, SHOW, EXPLAIN, INSERT, UPDATE, DELETE, CALL, cursors, CHECK TABLE.
  • Refused: CREATE, DROP, ALTER, RENAME, REFRESH VIEW, BACKUP DATABASE, USE, SET, users and grants (KarelaDB cannot roll these back), and BEGIN, COMMIT, ROLLBACK (the body is already a transaction). The message is atomic=1: CREATE TABLE cannot run inside a transaction ....
  • atomic=1 cannot be used with a session (X-KDB-Session): there, send BEGIN ... COMMIT yourself.
  • line and column of an error still count in the text you sent.
  • Other writers wait until the body is done, as with BEGIN ... COMMIT. Keep atomic bodies short.

def kareladb(sql, db=None, limit=10000):
    params = {"compat": 0, "limit": limit}
    if db:
        params["db"] = db
    r = requests.post("http://127.0.0.1:9900/exec", params=params, data=sql.encode("utf-8"),
                      headers={"Content-Type": "text/plain; charset=utf-8"})
    body = r.json()

    return body["results"]

async function kareladb(sql, db) {

static async Task<JsonElement> Kdb(string sql)
{
    var content = new StringContent(sql, Encoding.UTF8, "text/plain");
    using var res = await Http.PostAsync("/exec?compat=0", content);
    var json = JsonDocument.Parse(await res.Content.ReadAsStringAsync()).RootElement.Clone();

GET /exp

Syntax:

GET /exp?query=<SQL>[&db=<name>][&limit=N][&filename=<name.csv>]

Runs SQL that reads and answers with the rows of the last statement as a CSV file. A browser downloads it.

ParameterWhereMeaningDefault
queryURLSELECT, SHOW or EXPLAINrequired
dbURLThe database (or the header X-KDB-Database)the default database
limitURLMost rows: any number, also above a million (limit=50000000 for a whole big table). 0 or less means 1,000,000.1,000,000
filenameURLThe name of the downloaded file. Only letters, digits, -, _ and . are kept; at most 100 characters.kdb-export.csv
AnswerMeaning
Content-Type: text/csv; charset=utf-8a CSV file in UTF-8
Content-Disposition: attachment; filename="..."tells a browser to save it with that name
X-KDB-Rowsthe rows in the file
X-KDB-Truncatedtrue when limit (or the default of 1,000,000) cut rows off: more rows exist. false when the file holds every row
first linethe column names
next linesone row each; lines end with CR LF (\r\n, as Windows and Excel expect)
  • Status codes: 200 OK; 400 no query, bad SQL, or SQL that is not a SELECT, SHOW or EXPLAIN; 401/403 login or role; 404 unknown database.
  • Big exports are streamed. One SELECT of the columns of one table (with a WHERE, no ORDER BY, GROUP BY or join) is sent while it is read, so the server never holds the whole file: millions of rows go out at a few million rows a second, beyond max_result_memory. Once the file passes about 16 MB the answer is sent with Transfer-Encoding: chunked, and X-KDB-Rows and X-KDB-Truncated come at its end as trailer fields (Trailer: X-KDB-Rows, X-KDB-Truncated; curl -D - shows them after the body). A smaller file has them as headers. Other queries (ORDER BY, GROUP BY, joins, several statements) are made whole first, within the memory limits.
  • An error part way through a streamed export (the client left, the server stops) ends the connection without the last chunk, so the client sees a cut-off download, never a short file that looks whole.
  • Time: a streamed export is one statement until its last row is sent, so the statement timeout (kareladb serve --statement-timeout, 60 s by default) counts the sending too. For a very big table over a slow link, raise it or export by time ranges.
  • Notes: NULL is an empty field. Text with a comma, a quote, a line break, or a space at the start or end is put in "..." (a " inside becomes ""). Times are UTC like 2026-09-10T00:00:00.000Z. Errors are JSON (query, error, line, column), not CSV. /exp accepts only reading SQL even with POST, and does not use sessions.
