A transaction is a group of changes that KarelaDB saves together, or not at all. Nobody ever sees half of it.

Moving money is the classic case. A transfer is three changes: take money from one account, give it to the other, and write a ledger row (a row in the list of all transfers). If only the first change is saved, money is lost. Put them in a transaction.

  • Start it with BEGIN. Save it with COMMIT. Undo it with ROLLBACK.
  • When any statement in it fails, KarelaDB undoes the whole transaction.
  • KarelaDB writes the changes to its log (the file where every change is saved first) only at COMMIT, in one write. After a crash or a power cut, a committed transaction is there completely, and an unfinished one is not there at all.

Example: Accounting: a transfer between two accounts, then check the books

Setup:

CREATE TABLE accounts (
  id INT PRIMARY KEY,
  owner STRING NOT NULL,
  opening DECIMAL(2) NOT NULL,
  balance DECIMAL(2) NOT NULL
);
CREATE TABLE ledger (
  id LONG PRIMARY KEY AUTO,
  from_account INT NOT NULL REFERENCES accounts(id),
  to_account INT NOT NULL REFERENCES accounts(id),
  amount DECIMAL(2) NOT NULL,
  note STRING,
  created TIMESTAMP DEFAULT now()
);
INSERT INTO accounts VALUES (1, 'Ram', 1000, 1000), (2, 'Sita', 0, 0), (3, 'Hari', 500, 500);
BEGIN;
UPDATE accounts SET balance = balance - 250.50 WHERE id = 1;
UPDATE accounts SET balance = balance + 250.50 WHERE id = 2;
INSERT INTO ledger (from_account, to_account, amount, note) VALUES (1, 2, 250.50, 'rent');
COMMIT;

-- Check the books: the total never changes, and every balance matches the ledger.
SELECT sum(opening) AS money_at_start, sum(balance) AS money_now FROM accounts;
SELECT a.id, a.owner, a.balance,
       a.opening + coalesce(i.total_in, 0) - coalesce(o.total_out, 0) AS from_ledger,
       a.balance = a.opening + coalesce(i.total_in, 0) - coalesce(o.total_out, 0) AS ok
FROM accounts a
LEFT JOIN (SELECT to_account, sum(amount) AS total_in FROM ledger GROUP BY to_account) i ON i.to_account = a.id
LEFT JOIN (SELECT from_account, sum(amount) AS total_out FROM ledger GROUP BY from_account) o ON o.from_account = a.id
ORDER BY a.id;

BEGIN

Syntax:

BEGIN
BEGIN TRANSACTION
BEGIN WORK

Starts a transaction. The statements after it are saved only at COMMIT. BEGIN, BEGIN TRANSACTION and BEGIN WORK are the same.

  • Returns: transaction started.
  • Notes:
    • Inside the transaction you can use SELECT, INSERT, UPDATE, DELETE, CALL, SHOW ..., EXPLAIN, CHECK TABLE and cursors. Other statements are not allowed.
    • A SELECT inside the transaction sees its own changes. Other sessions do not see them until COMMIT.
    • Only one transaction can be open. A second BEGIN is an error, and the open transaction is rolled back.
    • While the transaction is open, other writers of the same tables wait (see one writer per table). Keep transactions short.
    • BEGIN cannot be used inside a procedure or trigger body: a CALL is already one transaction.
    • START TRANSACTION (the MySQL spelling) is not supported. Write BEGIN.

COMMIT

Syntax:

COMMIT
COMMIT TRANSACTION
COMMIT WORK

Saves every change of the open transaction, with one write to the log, and ends the transaction.

  • Returns: transaction committed: N change(s) saved. N counts the log records (about one per changed row, plus the changes made by triggers and procedures).
  • Notes:
    • When COMMIT returns OK, the changes are safe on disk, also after a crash or a power cut.
    • COMMIT without an open transaction is an error.
    • If the disk is full at COMMIT, it returns an error and nothing is saved.
    • In a session (kareladb shell, HTTP session) whose transaction was already rolled back by an error, COMMIT fails with COMMIT saved nothing, so your app cannot think it was saved.

ROLLBACK

Syntax:

ROLLBACK
ROLLBACK TRANSACTION
ROLLBACK WORK

Undoes every change of the open transaction and ends it. The data is exactly as it was before BEGIN.

  • Returns: transaction rolled back: N change(s) undone.
  • Notes:
    • Changes made by triggers and by CALLs inside the transaction are undone too.
    • ROLLBACK without an open transaction is an error, except in a session whose transaction was already rolled back by an error: there ROLLBACK ends it and answers transaction rolled back (it was already rolled back: ...).
    • Cursors declared inside the transaction stay open after ROLLBACK (their rows were read at DECLARE).

SAVEPOINT

Syntax:

SAVEPOINT name
ROLLBACK [WORK | TRANSACTION] TO [SAVEPOINT] name
RELEASE [SAVEPOINT] name

A savepoint is a mark inside BEGIN ... COMMIT. ROLLBACK TO undoes only the work after the mark; the work before it stays, and the transaction goes on.

StatementWhat it does
SAVEPOINT namemarks the point. A name used again marks a new point: the newest one counts.
ROLLBACK TO SAVEPOINT nameundoes every change after the mark. The mark stays, so you can go back to it again. Later marks are gone.
RELEASE SAVEPOINT nameforgets the mark and every later one. The changes stay in the transaction.
  • Returns: savepoint name set, rolled back to savepoint name: N row change(s) undone, savepoint name released.
  • Errors: outside BEGIN ... COMMIT: SAVEPOINT can only be used inside BEGIN ... COMMIT (PostgreSQL 25P01). A name that is not there: savepoint 'x' does not exist in this transaction (3B001).
  • Notes:
    • Nothing is saved until COMMIT. ROLLBACK (without TO) still undoes the whole transaction.
    • Rows for DEFERRED triggers that a ROLLBACK TO undid make no job.
    • Not inside a procedure or trigger body: the whole CALL is one transaction there.
    • Table locks stay until the transaction ends, also for tables only the undone part used (as in PostgreSQL).

After an error: ROLLBACK TO SAVEPOINT

In a session (an HTTP session, kareladb shell, the PostgreSQL protocol), an error after a savepoint does not throw the transaction away. As in PostgreSQL:

  1. The work after the newest savepoint is undone, and the transaction is aborted: every statement is refused with current transaction is aborted ... (25P02), except these.
  2. ROLLBACK TO SAVEPOINT name goes back to that mark and makes the transaction usable again.
  3. ROLLBACK ends it. COMMIT saves nothing and says so.

Without a savepoint, an error still rolls back the whole transaction (when a statement fails).

What is one transaction by itself

Syntax:

INSERT ... / UPDATE ... / DELETE ...    -- one statement: all its rows, or none
CALL procedure(...)                     -- the whole procedure
a statement that fires triggers         -- the statement and all its triggers

You do not always need BEGIN. These are each one transaction by themselves:

WhatAll or nothing
one INSERT, UPDATE or DELETEall its rows are written, or none (an INSERT of 1,000 rows with one bad row writes nothing)
one CALLevery change of the procedure, and of the procedures it calls (see procedures)
a statement that fires triggersthe statement and everything its triggers change
  • Notes:
    • Several statements without BEGIN are separate transactions. When the third one fails, the first two stay saved.
    • Inside BEGIN ... COMMIT, all of these become part of the bigger transaction.
    • At most 10 million changed rows in one transaction (DatabaseOptions::max_transaction_rows). Until COMMIT, KarelaDB keeps the old version of every changed row in memory.
    • A long transaction's log records go to a temporary file once they pass 64 MB (see big transactions).

When a statement fails

Syntax:

BEGIN; statement; failing statement;   -- the whole transaction is rolled back here

When a statement inside BEGIN ... COMMIT fails (a duplicate key, REFERENCES, a CHECK, RAISE in a procedure or trigger, a typing error in a column name, ...), KarelaDB rolls back the whole transaction at once.

  • Returns: the error of the statement, with (the transaction was rolled back) at the end.
  • Notes:
    • In one text (kareladb sql, POST /exec, the web console), the statements after the error do not run.
    • In a session (kareladb shell, an HTTP session, the PostgreSQL protocol) the session then accepts only ROLLBACK (or COMMIT, which fails). So your next statements cannot run outside the transaction by mistake.
    • With a savepoint set, the error undoes only the work after it, and ROLLBACK TO SAVEPOINT lets the transaction go on.
    • A syntax error is found before anything runs: then no statement of the text runs at all.

A text that ends without COMMIT

Syntax:

BEGIN; statement; ...   <end of the text>   -- rolled back

kareladb sql, POST /exec without a session, and the web console run one text at a time. A transaction cannot stay open after its text ends: when the text ends without COMMIT or ROLLBACK, KarelaDB rolls it back and returns an error.

  • Returns: the error BEGIN without COMMIT: the transaction was rolled back (end it with COMMIT to save the changes), after the results of the statements that ran.
  • Notes: in kareladb shell, in an HTTP session and over the PostgreSQL protocol, the transaction stays open until you send COMMIT or ROLLBACK (or leave). Leaving the shell or closing the session rolls it back.

Statements not allowed inside a transaction

Syntax:

CREATE ...  DROP ...  ALTER ...  RENAME ...  BACKUP DATABASE   -- before BEGIN or after COMMIT

Changes of the database structure cannot be undone like rows, so they are refused inside BEGIN ... COMMIT: CREATE / DROP / ALTER of tables, views, indexes, functions, procedures and triggers, RENAME TABLE, and BACKUP DATABASE. Run them before BEGIN or after COMMIT.

  • Returns: the error CREATE TABLE cannot be used inside a transaction; COMMIT or ROLLBACK first. The open transaction is rolled back.
  • Notes: the same statements are also not allowed inside a procedure or trigger body.

SELECT ... FOR UPDATE

Syntax:

SELECT columns FROM table WHERE ... FOR UPDATE

A SELECT that says: "I read these rows because I will change them". Write it at the start of a transaction, before the UPDATEs.

  • Returns: the rows, like a normal SELECT.

  • Notes:

    • On a table with a primary key, FOR UPDATE locks the rows it returns, until your transaction ends (COMMIT, ROLLBACK, the session closing, or the idle limit). The rest of the table stays free: other sessions read it, change other rows, and lock other rows with their own FOR UPDATE.

    • Another transaction that wants one of your locked rows:

      It runsWhat happens
      SELECT ... FOR UPDATEwaits until your transaction ends (up to the lock timeout)
      SELECT ... FOR UPDATE NOWAITfails at once: could not obtain lock on row in relation "jobs" (HTTP 503, PostgreSQL 55P03)
      SELECT ... FOR UPDATE SKIP LOCKEDleaves your rows out and returns the next free ones; LIMIT and OFFSET count after the skipping
      UPDATE or DELETE of the rowwaits until your transaction ends (up to the lock timeout)
      a plain SELECTreads it at once: row locks never stop a reader

    • So a job queue works with many workers: each one runs BEGIN; SELECT ... ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED, does the job, then UPDATE ...; COMMIT, and no two workers get the same job.

    • Two transactions that each wait for a row the other one locked get deadlock: ... at once (PostgreSQL 40P01) instead of both waiting. Roll back and try again.

    • A row your transaction changed (UPDATE, DELETE, INSERT) is still locked with its whole table until COMMIT, as every change is. Meanwhile:

      Another session runsWhat happens
      SELECT ... FOR UPDATE SKIP LOCKED inside its own BEGINwaits a moment (50 ms) and then returns no rows
      SELECT ... FOR UPDATE SKIP LOCKED without BEGINskips the rows you locked and the rows you changed, and returns the next free ones at once, as in PostgreSQL. It keeps no lock on them. Rows you added are not seen until COMMIT.
      SELECT ... FOR UPDATE NOWAITfails at once with table 'x' is busy

      So in a job worker, do the work first and send the UPDATE just before COMMIT: then the jobs table is held only for a few milliseconds. A worker that marks its job running early and then works on it makes the queue look empty to the others until it commits.

    • kareladb serve --skip-locked-beside on (off by default) makes SKIP LOCKED inside BEGIN return the free rows too, and lock them. The catch, until a change stops holding the whole table: the row you got is not free for your UPDATE. That UPDATE waits for the other transaction's COMMIT, and fails with 40001 after the lock timeout (5 seconds unless set) when that transaction stays open longer. If the other transaction then changes that row too, one of the two gets deadlock: ... at once. Turn it on only when your workers commit quickly and retry 40001 and deadlock.

    • With either setting, SKIP LOCKED returns no rows while another transaction holds the table in a way that names no rows: a FOR UPDATE that locks tables (a join, a subquery), a change of more than 4,096 rows of the table, a DELETE of every row or a bulk load. It also returns no rows when the table is held by a statement that is running right now for more than 50 ms.

    • On a table without a primary key there is no key to lock a row by: FOR UPDATE locks the whole table until your transaction ends, and SKIP LOCKED returns no rows while another transaction holds it.

    • Without BEGIN (no transaction), FOR UPDATE locks the rows only while the statement runs.

    • FOR UPDATE goes at the very end of the SELECT, after ORDER BY and LIMIT. Row locks are taken for a SELECT from one table; with a join, GROUP BY, DISTINCT or a view it locks the tables, as before.

    • FOR SHARE, FOR NO KEY UPDATE and FOR KEY SHARE take the same lock as FOR UPDATE, with NOWAIT and SKIP LOCKED too. In PostgreSQL two sessions may both hold FOR SHARE on one row; in KarelaDB the second one waits (or NOWAIT fails, or SKIP LOCKED skips the row). That is stricter, never looser: nothing gets through that PostgreSQL would stop. It is only slower when many readers share rows.

One writer per table

Syntax:

session A: BEGIN; UPDATE accounts SET ... WHERE id = 1;  -- A locks row 1 of accounts (row-level locks)
session B: INSERT INTO ticks ...;                         -- B goes at once: another table
session C: UPDATE accounts SET ... WHERE id = 2;          -- C goes at once: another row
session C: UPDATE accounts SET ... WHERE id = 1;          -- C waits for A's row (5 s unless set), then "a row of table 'accounts' is locked"
session C: SELECT ... FROM accounts;                      -- C does not wait for A's open transaction: it reads the data without A's changes
session A: COMMIT;                                        -- row 1 is free; the next writer goes

A reader waits only while a writer's statement runs (see reader yield for long triggers and CALLs). Between A's requests nothing runs, so C reads at once.

A writer locks every table it uses until its statement ends. Inside BEGIN ... COMMIT it keeps them until the transaction ends - except where it only updated rows by their key: there it holds just those rows (row-level locks, in the table below). Writers of different tables run at the same time. Writers of the same table take turns, so two transfers can never mix, and every transaction sees the data exactly as the one before it left it (this is called serializable).

RuleDetail
Other tablesWriters of different tables do not wait for each other's locks: a live tick feed and a big load into another table run side by side. They can still wait a little for work the whole database shares: a checkpoint that writes the changes to disk, and the disk sync of a commit.
The same tableA second writer waits until the first one ends, first come, first served. Line-protocol writes and bulk loads wait the same way.
What is lockedThe tables a statement changes and reads, and what it sets off: tables its triggers and procedures use, tables linked to it by foreign keys, and _audit_log for audited tables. A procedure or trigger whose EXECUTE text is made while it runs (format(...), '...' || name), and a read of information_schema or pg_catalog in a writer, lock every table. EXECUTE of text written out in the body locks only the tables of that text.
Row-level locksInside BEGIN ... COMMIT, an UPDATE of rows of a table with a primary key locks those rows, not the table, until the transaction ends. Between its statements the transaction gives the table back: another transaction may change other rows of it at once, and one that meets a locked row waits for it, as in PostgreSQL (after the lock timeout: a row of table 'x' is locked, 55P03, or 40001 inside its own transaction). Two transactions that wait for each other's rows: one gets deadlock: ... at once. A ROLLBACK puts back only its own rows. What still keeps the whole table until COMMIT: an INSERT or DELETE in it, an UPDATE that changes a row's key, and any change of a table with another UNIQUE column or unique index, a foreign key (either way) or a trigger - rows the transaction holds could clash with another writer's there. A read in another transaction does not hold up such a transaction. Turn it off with KARELADB_NO_ROW_LOCKS=1 (every table a transaction writes stays locked until it ends, as before).
SELECT ... FOR UPDATEOn a table with a primary key it locks only the rows it returns, not the table, until the transaction ends: other writers of the table go on, and only a writer of one of those rows waits (row locks).
Several writers at oncekareladb serve --table-writers many: requests that touch a table only by single rows and their primary key run on it at the same time, waiting only for the same row (several writers of one table). Off by default.
Several tablesThe tables of one request are locked all at once, always in the same order, so two such requests never wait for each other.
DeadlockA transaction that needs one more table in a later request can meet another transaction that waits for one of its tables. KarelaDB sees this at once: the one that would wait gets deadlock: ... (HTTP status 503) and is rolled back. Run it again.
BusyA writer that waited the lock timeout (5 seconds unless set) gets table 'x' is busy: ... (HTTP status 503, PostgreSQL 55P03; 40001 inside its own BEGIN ... COMMIT, see isolation). Nothing of its statement was done: try the whole transaction again a moment later.
A taken keyAn INSERT ... VALUES that waits for a busy table looks its keys up in the committed rows while it waits. A key that is already there gives the duplicate key error at once (PostgreSQL 23505, HTTP status 400, with the table and constraint named), not 55P03 after the lock timeout. Inside BEGIN the transaction ends, as after any 23505. A key that only the other transaction has added, deleted or changed is not decided yet: the INSERT waits for it. When that transaction commits, the INSERT gets 23505 (if the key is now taken) or goes in; when it rolls back, the row goes in. A key it deleted is never reported as taken. This covers the primary key, UNIQUE columns, plain unique indexes and a time-series DEDUP KEY that includes the time column, with literal values or $1 parameters (not values worked out by an expression, ON CONFLICT, or a table with an INSERT trigger: those wait as before).
Schema changes of a tableCREATE TABLE, ALTER TABLE (RENAME too), DROP TABLE, CREATE INDEX, DROP INDEX, CREATE, ALTER and DROP TRIGGER and TRUNCATE lock only their table (and the tables its foreign keys point at). CREATE TABLE ... AS locks the tables its query reads. CREATE, REFRESH and DROP MATERIALIZED VIEW lock the view and its table. They wait for writers of that table, like any writer (table 'x' is busy: ...). CREATE TABLE (also IF NOT EXISTS and AS SELECT), ALTER TABLE (not SET TTL, SET (dedup_insert ...) or DEDUP), RENAME TABLE and CREATE / DROP INDEX do not wait for writers of other tables at all: they run beside them, also beside one long INSERT ... SELECT, COPY or CALL that never pauses. Only a writer that named the new table before it existed is waited for. The other schema changes of a table (DROP TABLE, triggers, TRUNCATE, materialized views) wait for a long writer of other tables only until it pauses between two of its statements (reader yield). Only the wait for writers counts against the lock timeout: a long SELECT or read-only CALL is waited for as long as it runs, then the schema change runs. Readers wait while the schema change itself runs, which is short. Turn it off with kareladb serve --ddl-beside-writers off (they wait for the pause again) or --scoped-ddl off (every schema change locks every table).
Views, procedures, functionschange a definition, not a table: they lock no table, and writers of tables go on (creating or altering a CACHED view and REFRESH VIEW lock the tables its query reads). They still wait for a writer that may use the old definition next: a view change for a running writer that reads a view, a procedure or function change for a running writer that runs a procedure, a function or a plpgsql trigger (a long CALL, say). Other schema changesSequences, BACKUP, DEDUP TABLE, a change of a table a materialized view reads, a CREATE TABLE ... AS whose query reads information_schema, and a schema change sent in one request with statements it affects (CREATE OR REPLACE PROCEDURE p ...; CALL p(), or CREATE VIEW v ...; INSERT ... SELECT FROM v) lock every table: they wait until no transaction is open, and after the lock timeout get database is busy: .... While such a change waits for a writer that was already running, writers of other tables still go ahead of it. Once that writer ends, new writers wait behind the change, so it is never kept out.
Schema statements with nothing to dolock nothing and answer at once: CREATE TABLE IF NOT EXISTS of a table that is there, ALTER TABLE ... ADD COLUMN IF NOT EXISTS of a column that is there, DROP COLUMN IF EXISTS, DROP TABLE IF EXISTS, DROP INDEX IF EXISTS and DROP VIEW IF EXISTS of something that is not there, CREATE INDEX IF NOT EXISTS and CREATE VIEW IF NOT EXISTS of one that is there, CREATE EXTENSION, and a COMMENT ON that changes nothing (the same text again, or an object whose comments KarelaDB does not keep). So the CREATE ... IF NOT EXISTS an app sends at start-up never waits for a long writer.
A request that cannot get its locksnone of its statements ran. The error says so: ... (none of the 2 statements of this request was run). Send the whole request again.
Readers and open transactionsA SELECT does not wait for an open transaction between its requests: it runs at once and sees the data without that transaction's changes. A read never waits for another read.
Readers and a running writerA SELECT waits only while a writer runs on a table it reads (a statement, a long CALL, a trigger, a POST /write). SELECT 1, a login lookup and reads of other tables answer at once (readers during a long writer). With reader yield (on unless turned off), a long CALL, trigger or request of many statements lets readers of its tables in between its statements; with it off, they wait for the writer's whole request.
A CALL that only readsis a reader, not a writer: it locks nothing, like a SELECT (a CALL that only reads).
What a reader seesthe last committed state when its request starts, for every table at once. A commit that changes several tables (a trigger that fills three tables) is seen whole or not at all. The statements of one read-only request all see the same state.
IdleA transaction with no statement for 30 seconds is rolled back, so a forgotten transaction cannot block everybody. The time is a setting: see idle transactions.
CommitsWriters that commit at the same moment share one wait for the disk (group commit). Each one is still told "committed" only when its changes are on the disk - unless its session set SET synchronous_commit = off (performance tips): then it is told at once and the disk follows within about 10 ms.
Per databaseThe locks are for one database. Transactions on other databases do not wait.
  • Notes: a transfer takes about a millisecond, so waiting is short. Never keep a transaction open while you wait for a person (a click, a form, an SMS code). Read first, ask the person, then do BEGIN ... COMMIT quickly.
  • Use the tables in the same order in every transaction (for example accounts, then ledger), or send the whole transaction in one request. Then deadlocks cannot happen.

Isolation: what a transaction sees

Syntax:

BEGIN [ISOLATION LEVEL READ COMMITTED | SERIALIZABLE]
SET TRANSACTION ISOLATION LEVEL READ COMMITTED        -- this transaction only (inside BEGIN)
SET default_transaction_isolation = 'read committed'  -- the session's transactions from now on
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL READ COMMITTED
SHOW transaction_isolation

KarelaDB's transactions are serializable unless you ask for READ COMMITTED: every table a transaction reads or writes is locked until COMMIT or ROLLBACK. PostgreSQL's default is READ COMMITTED.

Read-only transactions

Syntax:

BEGIN READ ONLY                               -- also START TRANSACTION READ ONLY (PostgreSQL port)
BEGIN ISOLATION LEVEL READ COMMITTED, READ ONLY
SET TRANSACTION READ ONLY | READ WRITE        -- this transaction only (inside BEGIN)
SET default_transaction_read_only = on | off  -- the session's transactions from now on
SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY
SHOW transaction_read_only

A read-only transaction refuses every change, as in PostgreSQL. Use it for reports and checks that must never write by mistake.

In a read-only transactionResult
SELECT, SHOW, EXPLAIN, cursors, a CALL of a procedure that only readsruns
INSERT, UPDATE, DELETE, TRUNCATE, COPY ... FROMrefused
CREATE, ALTER, DROP of tables, views, indexes, procedures, databases and usersrefused
SELECT ... FOR UPDATE, WITH x AS (UPDATE ...), nextval(), setval()refused
a CALL or DO block whose body changes datarefused at the first change
  • The error: cannot execute INSERT in a read-only transaction, SQLSTATE 25006 (HTTP 403). Inside BEGIN ... COMMIT the transaction is aborted, as in PostgreSQL: send ROLLBACK. Nothing is written.
  • Notes:
    • With default_transaction_read_only = on, a statement sent on its own is read-only too. BEGIN READ WRITE (or SET TRANSACTION READ WRITE first in the block) writes once, for that transaction.
    • SET TRANSACTION READ WRITE after the transaction ran a query is refused (25001), as in PostgreSQL.
    • Over HTTP, BEGIN READ ONLY works in one request. SET default_transaction_read_only and SET TRANSACTION need an HTTP session (POST /session): without one there is nowhere to keep them, so they are refused.
    • One session's setting never changes another session.
    • To make a whole database or server read-only for everyone, use ALTER DATABASE ... SET READ ONLY or kareladb serve --read-only instead.

LOCK TABLE, pg_locks and lock waits

Syntax:

RuleDetail
Only in a transactionOutside BEGIN ... COMMIT it fails with LOCK TABLE can only be used in transaction blocks (25P01), as in PostgreSQL. In a procedure body it lasts until the request's transaction ends.
NOWAITA table another transaction holds in a conflicting mode fails at once with could not obtain lock on relation "t" (55P03, HTTP 503: try again), and the transaction is rolled back, as in PostgreSQL. Without NOWAIT it waits the lock timeout.
A viewlocks the tables the view reads, in the same mode.
KarelaDB's own writersstill take turns on a table as always (one writer per table): two UPDATEs of one table never run at once. pg_locks shows a writer's lock as RowExclusiveLock (it changes the table), RowShareLock (SELECT ... FOR UPDATE) or AccessShareLock (it reads the table in its transaction).
ReadersA plain SELECT waits only for ACCESS EXCLUSIVE. A read that started before the lock was granted runs to its end. The session that holds the lock reads on.
DeadlockTwo transactions that wait for each other: one gets deadlock: process 12 waits for ExclusiveLock on table 't1'; blocked by process 34. Process 34 waits for ... (40P01, HTTP 503) at once and is rolled back. Run it again.
RightsACCESS SHARE needs the right to read the table; the other modes the right to change it. A read-only transaction may take up to ROW EXCLUSIVE.

pg_locks lists the table locks of the database: one row per table and mode, granted true for a held lock and false for one waited for (then waitstart says since when). pid is the same number pg_stat_activity and pg_backend_pid() give for that connection or HTTP session. A lock of every table (a schema change, BACKUP) shows as AccessExclusiveLock on each table. Over the PostgreSQL port relation::regclass gives the table's name; over HTTP join pg_class on oid.

pg_locks, pg_stat_activity and pg_stat_statements read no table, so a transaction can look at them (BEGIN; LOCK TABLE t; SELECT * FROM pg_locks) without taking any other table and without waiting for anyone.

pg_blocking_pids(pid) gives the pids a waiting pid waits for: those holding a lock in its way, and those that came first and wait for the same table. {} when it does not wait.

log_lock_waits (off by default) writes one line to the server log when a statement has waited for a table lock longer than deadlock_timeout (1 second by default), naming it, the lock, who holds it and who waits: kareladb: LOG: process 12 still waiting for RowExclusiveLock on relation 16448 ('t') of database 'main' after 1003 ms; process holding the lock: 34; wait queue: 12. Set it for the server with kareladb serve --log-lock-waits on --deadlock-timeout 1s (KARELADB_LOG_LOCK_WAITS, KARELADB_DEADLOCK_TIMEOUT), or for one session with SET. KarelaDB finds a deadlock at once whatever deadlock_timeout is: it only says when the line is written.

Idle transactions: idle_in_transaction_session_timeout

Syntax:

kareladb serve --idle-in-transaction-timeout 5min    the server (default 30s; 0 = never)
KARELADB_IDLE_IN_TRANSACTION_TIMEOUT=5min            the same, for Docker
"idle_in_transaction_timeout_ms": 300000        the same, in kareladb.conf
SET idle_in_transaction_session_timeout = '5min' | 300000 | 0 | DEFAULT   one session

An open BEGIN ... COMMIT that sends no statement for this long is rolled back. This happens when another writer needs its tables, or at its own next statement. Its session then gets an error until it sends ROLLBACK. So a client that died in the middle of a transaction cannot keep its tables locked for ever.

Readers of the writer's tables: reader yield

kareladb serve --reader-yield on|off        (default on)
KARELADB_READER_YIELD=off                   (the same, for Docker; a flag wins)

A writer's request can run for many seconds: a CALL that builds a day of candles, an immediate trigger, a request with many statements. Readers never see its changes before it commits. Readers of other tables never wait for it (above). For readers of its tables, this switch decides whether they wait meanwhile. The start-up lines say which one is in use (readers ...).

offon (default)
A SELECT of the writer's tables while it runswaits until the writer's request endsanswers soon, with the rows as the last commit left them
Howreaders and writers take turns at the databasebetween two statements of the writer's body or request, the writer steps aside and lets waiting readers in. Its table locks stay, so no other writer gets its tables.
Costnonea pause is free when nobody waits. A reader of a table the writer already changed makes the writer take its changes out and put them back, so the writer keeps at least about two thirds of its time.

    • The pause comes only between statements. One long statement (a big INSERT ... SELECT, a big UPDATE) still makes readers wait until it ends.

    • Writers of other tables do not need this switch: they never wait for each other.

Readers of the writer's tables: snapshot reads

Syntax:

kareladb serve --snapshot-reads on|off      (default off)
KARELADB_SNAPSHOT_READS=on                  (the same, for Docker; a flag wins)

With snapshot reads on, a reader of a table that a writer is changing does not wait, not even for one long statement. It reads a snapshot of the table: the rows committed when the read started.

reader yield onlysnapshot reads on
A SELECT of t while a long CALL, trigger job or INSERT ... SELECT writes twaits for the statement running nowanswers at once, with the committed rows
A SELECT of t while a session's BEGIN holds changes of tanswers at once (the transaction is taken out for it)answers at once (the transaction stays in)
A read-only CALL of twaits like a SELECTreads snapshots, each statement of its body the rows committed when it starts
What the writer paystakes its changes out and puts them back for readersnothing: when a reader holds a snapshot of a partition it changes next, it leaves the snapshot's unsaved rows as they are and writes on a new layer on top (since 2026-10-02; before, it copied them all)
  • Notes:
    • A writer that is about to finish (within 20 ms, a short write and its disk sync) is still waited for: a snapshot for every read of a table written many times a second would slow its writer down. Once a snapshot is taken, readers during the same long writer use it at once.
    • A snapshot never holds uncommitted rows, and never half of a commit: all the tables of one transaction or none of them.
    • A snapshot waits until the rows it holds are on disk, as the writer that made them does.
    • Tables with an index get snapshots too, while a writer is busy on them, at any size (since 2026-10-02). A read of the snapshot still uses a plain or expression index (CREATE INDEX): it checks each row the index finds against the snapshot, and also finds the rows the writer changed or deleted since. So a lookup stays a lookup, never sees an uncommitted row, and EXPLAIN shows the index as usual.
    • A full-text or JSON index is not used on a snapshot, and neither is an index that is not built in memory yet (after a restart, before its first use): such a read scans the snapshot instead. A table like that with more than 1,000,000 rows is not scanned: its readers wait for the writer, as before. --snapshot-index-rows N (KARELADB_SNAPSHOT_INDEX_ROWS) moves that line; 0 means indexed tables never get snapshots.
    • An open transaction that sits idle (BEGIN, a change, then nothing) gives readers of an indexed table no snapshot: they take it out of their way and use the index on the table itself, as without snapshot reads.
    • Materialized views are still read as before (the reader waits).
    • One statement that writes a table applies its rows in one step at the end. A reader of that same table waits for that step (up to about a second per million rows), never for the whole statement.
    • Readers that use a snapshot, snapshots taken and snapshots reused show in GET /api/stats (snapshot_reads, snapshots_taken, snapshots_reused).
    • GET /api/stats itself reads snapshots too (since 2026-10-02): the row counts of a table a writer is changing are its committed rows, and it answers at once instead of saying "busy": true until the writer is done.
    • Layers (since 2026-10-02). The unsaved rows of a partition (changed since the last checkpoint) are shared between the table and its snapshots. A writer that changes such a partition freezes them as a layer and writes on a new one, so its cost is the rows it writes, not the rows the partition holds. Reads merge the layers. When no snapshot holds a layer any more, the next write to the partition folds it back; a checkpoint folds them all. A partition keeps at most 6 layers: past that, the two smallest neighbours become one.
    • GET /api/stats counts them since the server started:
FieldWhat it counts
snapshot_delta_freezeslayers frozen because a snapshot held them when a writer came
snapshot_delta_foldslayers folded back once no snapshot held them
snapshot_delta_mergespairs of layers made one (past 6 layers in a partition)
snapshot_delta_copiesfull copies of a partition's unsaved rows (only an ALTER TABLE makes one now)
snapshot_delta_layersfrozen layers the tables hold right now (0 when the stats are read while a job runs)

A snapshot_delta_layers that stays high while nobody reads means a partition was not written since its last snapshot ended: the next write or checkpoint frees it.

Syntax:

With many, several users change one table at the same time, as long as each of their requests touches the table only by single rows and their primary key:

The table must be a plain table with a one-column PRIMARY KEY, no foreign key either way, no other UNIQUE column or index, no AUTO column, no FOR EACH ROW trigger and no materialized view built from it (statement triggers are fine). Other tables of the same request are not affected: each is held shared or whole on its own.

  • What you get: eight users running a bank-transfer CALL no longer take turns on the accounts table; their statements overlap and more of their commits share one disk sync.
  • The same row: a second writer of a row waits for the first one's end (the lock timeout applies), then reads the row as that writer left it, committed or rolled back: balance = balance - 10 twice gives the same balance as one after the other, as PostgreSQL's row locks do. Two inserts of one key give one row and one already exists (23505). A read of a row by its key (SET v = (SELECT ... WHERE id = x)) waits for another writer of the row and then keeps the row until its own request ends, as an UPDATE does: a request never sees a change that is not committed, and a procedure that checks what it read before it changes the row (IF bal < amt THEN RAISE ...; UPDATE ...) is as exact as with one writer per table - two calls cannot both pass on the same old balance. The row is kept even when the request only reads it: calls that all read one busy row by its key (a rate looked up by SET r = (SELECT rate FROM fx WHERE ccy = x)) take turns on that row until each one commits, as they would with one writer per table. The disk sync is not part of that wait.
  • Deadlock: two writers that wait for each other's rows get deadlock: ... (40P01) at once, like two transactions that wait for each other's tables. Run the request again.
  • Readers: a SELECT of the table waits for all of its writers, or reads a snapshot with snapshot reads on; it never sees half a statement.
  • The escape hatch: a request that turns out to need more of the table than its statements showed (rare) takes the whole table for itself, waiting for the other writers to end; GET /api/stats counts it in shared_writer_upgrades, next to shared_writers (requests that held a table shared) and shared_row_waits. The rows it read by key stay kept while it waits, so if another writer is changing one of them, one of the two gets deadlock at once. Run it again.

Big transactions: log records on disk

Syntax:

kareladb serve --txn-spill-mb 64            (default 64; 0 = never)
KARELADB_TXN_SPILL_MB=64                    (the same, for Docker; a flag wins)

A transaction writes its changes to the log only at COMMIT. Until then KarelaDB keeps the log records (the changes, ready to be written). A long CALL, a deferred trigger job or a big BEGIN ... COMMIT can make many of them.

Since 2026-10-02, once they pass 64 MB, KarelaDB moves them to a temporary file in the database's _tmp folder. Only where each record starts stays in memory.

WhenWhat happens to the file
COMMITread back in order and written into the log, then removed
ROLLBACKremoved
ROLLBACK TO SAVEPOINTcut back to where the savepoint was
a crashremoved when the database opens again (those records were never committed)
  • Notes:
    • With a memory limit (--memory-limit), the line is at most 1/16 of it. Under a 512 MB limit that is 32 MB.
    • Only the log records go to disk. The changed rows themselves stay in memory until COMMIT, so a transaction still stops at a quarter of the memory limit ("transaction too big for memory") when its rows alone need that much.
    • Example: one CALL that inserts 2 million rows under a 512 MB memory limit was stopped at 1.5 million rows. With its 64 MB of log records on disk it finishes, and the heap stays near 230 MB.
    • A commit of spilled records always waits for the disk, even with SET synchronous_commit = off.
    • GET /api/stats counts them per database: txn_spills (transactions that used a file) and txn_spilled_bytes.
    • 0 keeps every record in memory, as before.

Accounting with CHECK constraints

Syntax:

balance DECIMAL(2) NOT NULL CHECK (balance >= 0)
BEGIN; UPDATE ...; UPDATE ...; INSERT INTO ledger ...; COMMIT;

A CHECK constraint (a rule that every row must follow, see constraints) makes the database itself refuse a balance below zero. Together with a transaction, a transfer that would break the rule saves nothing.

Checklist for money:

  1. Money columns are DECIMAL(2) NOT NULL (exact, never DOUBLE), with CHECK rules for what must never happen.
  2. Keep a ledger. Never update or delete its rows; correct a mistake with a new transfer back.
  3. Every transfer: BEGIN, UPDATE ... SET balance = balance - amount, UPDATE ... + amount, INSERT INTO ledger, COMMIT. Let the database do the math; do not write a balance that your app computed.
  4. On any error: ROLLBACK. On table ... is busy, database is busy or deadlock: run the whole transaction again.
  5. Check the books every night (the total, and every balance against the ledger), like in the first example of this page.

Example: A transfer of more than the balance saves nothing (shows an error)

Setup:

CREATE TABLE accounts (
  id INT PRIMARY KEY,
  owner STRING NOT NULL,
  balance DECIMAL(2) NOT NULL DEFAULT 0 CHECK (balance >= 0)
);
CREATE TABLE ledger (
  id LONG PRIMARY KEY AUTO,
  from_account INT NOT NULL REFERENCES accounts(id),
  to_account INT NOT NULL REFERENCES accounts(id),
  amount DECIMAL(2) NOT NULL,
  CONSTRAINT positive_amount CHECK (amount > 0)
);
INSERT INTO accounts VALUES (1, 'Ram', 749.50), (2, 'Sita', 250.50);
BEGIN;
UPDATE accounts SET balance = balance + 900 WHERE id = 2;
UPDATE accounts SET balance = balance - 900 WHERE id = 1;
INSERT INTO ledger (from_account, to_account, amount) VALUES (1, 2, 900);
COMMIT;
