Monitor panel (memory, processor, caches)

What the server is doing right now - memory it holds, processor it uses, what each database keeps in memory, deferred trigger queues, and the statements running this second.

The Monitor panel of the web console shows the inside of a running kareladb serve: how much memory the process holds, how busy the processor is, what each open database keeps in memory, and which statements are running right now. Open it with the Monitor button on the right side of the console. It is a panel, not a page: pin it to keep it open beside the page you work on.

It reads GET /api/stats every couple of seconds. Everything there is a counter already in memory, so asking often costs almost nothing: no file is read and no database is opened to answer it.

  • Any login that may read can see the panel. A read user sees only their own running statements, because statement text can hold values; an admin sees everyone's.
  • Refresh at the top picks 2, 5, 10 or 30 seconds, or Off; Now reads the numbers at once. The panel stops asking while it is closed or the browser tab is hidden.
  • /api/stats holds more than the panel shows, for example the zone map counters (zone_partition_skips, zone_block_skips), cache_pinned and the memory of each database by kind. Read it from a script for those (GET /api/stats).

Warnings and databases opening

At the top, in a yellow frame, the server's warnings: today, a database far bigger than --memory (why it matters).

Below them, one card per database being opened right now. A big database replays the log written after its last checkpoint, which over a slow disk takes minutes, and its first request waits that long. The card shows what the open does now (checking log, replaying log, loading tables, ...), for how long, how much of the log is replayed, and how many table files it went through. When the numbers move, the open is working; the card goes away when the database is open.

In a database's card, a Checkpoint line shows a checkpoint writing changes to partition files: the table, partitions written of how many, and for how long. Busy means a write or a checkpoint held the database when the panel asked: the memory numbers are live, the tables and queues are from the reading before. The panel never waits for a busy database.

The server process

NumberWhat it means
Memory in RAMwhat the operating system says this process holds now (Windows: working set; Linux: VmRSS). The bar is its share of the RAM in the computer.
Most it ever heldthe highest that number has been since the server started
Processorshare of one processor used between the last two readings. 100 % means one processor fully busy; on 8 processors the most is 800 %. It is blank until the panel has asked twice.
Running forhow long the process has been up
Threadsthreads the process runs now: the query threads (--threads), the HTTP server (one thread that accepts connections and a pool of workers that answer requests, --http-threads), the PostgreSQL port, and the background threads (checkpoints, timers, the audit log)
Open handlesopen files and sockets
Free RAM on this computerwhat a program could still get. Inside a container this is the container's limit, not the host's RAM.
Processorsprocessors the process may use

Memory in RAM is bigger than the memory budget below it: the budget covers table data, while the process also holds indexes, results being built, and the program itself.

Statements running now

One line per statement, over HTTP and the PostgreSQL port together:

ColumnWhat it is
Elapsedhow long it has been running
Lanefast, normal or heavy (priority lanes); heavy (waiting) while a report waits for a heavy slot
Userthe user who sent it, or (token) for the access token
Databasewhich database it runs against
Fromthe address it came from, and which port (http or pg)
Statementthe first 200 characters
Cancelstops it: DELETE /exec/<id>. It becomes stopping until it winds down.

Cancel needs a name to cancel by, which is the X-KDB-Request-Id header the client sent. A client that sent none shows no id instead; it still stops on its own statement timeout. The console itself always sends one. There is no Cancel at all on a server started without query protection (can_cancel is false in /api/stats).

A statement that is stuck is usually one of the things in performance tips: a SELECT with no time range on a big time-series table, a join without a matching key, or a GROUP BY over too many groups.

Lanes

Shown while priority lanes are on: the heavy slots in use, how many reports wait for one, how many statement shapes are known to be heavy, and whether heavy statements run at a lower CPU priority here. The table has one line per lane: how many run and wait now, how many started since the server did, how many had to wait and for how long (average and longest), how many were refused because the HTTP line was full (only requests sent with priority low), how many ran at once because it was full (heavy only by history), and how many gave up waiting (a timeout or a cancel).

Slow statements

The newest 20 statements that took at least the slow-query threshold (kareladb serve --slow-query-ms, 1 second by default), from GET /api/slow-queries. They are kept in a file on disk, so last night's slow statement is still here in the morning, after a restart too.

ColumnWhat it is
Whenwhen it ended
Tookhow long it ran
User, Databasewho sent it (the token's name for the access token), and where
Statementthe statement; failed: in front when it did not succeed. Point at it for the whole text and the error.

The list is read every 10 seconds at most, and at once with Now.

Timers

Every timer of the databases you may read, also of databases not open yet. Timers in trouble come first: failing now, then failed in the last 24 hours, then the latest to start. The title counts the timers with failures.

ColumnWhat it is
Timerdatabase.name; (off) when it is turned off. Point at it for the schedule, the next run and the SQL.
Last runhow long ago it last ran and whether that run was ok or failed (red); running now while it runs
Latehow many seconds after its due time the last run got its write in; yellow above 5 s. Point at it for the worst since the server started.
Failed 24 hruns that failed in about the last 24 hours (red when not 0). Point at it for the count since the server started.
Last errorthe last run's error, or -

The numbers come with the rest of /api/stats (timers), from memory: nothing is read from disk for them.

Each database

Only databases that are open are listed. A database opens the first time it is used, so a server that has just started may show none - that is not a fault.

NumberWhat it means
Rows held in memorysaved partition data kept in memory, against the budget (--memory, 512 MB by default). When it is full, the partitions used longest ago are dropped and read again when next needed.
Waiting to be writtenchanges that are in the log but not yet in the partition files. A checkpoint writes them; it starts by itself at a quarter of the memory budget.
Result cachememory holding results of repeated queries (--cache-mb or cache_mb in kareladb.conf, 256 MB by default; 0 turns it off)
Cache hitsshare of queries answered from that cache since the database was opened
Cached resultshow many results are in that cache now
Open cursorscursors a client has open (POST /cursor)
Log positionthe last change written to the log (the LSN)
On diskwhat the database takes on disk. The bar is the share that is data; point at it for the parts: data, older versions, trash, log, old log. Measured once a minute. Older versions and trash go by themselves (keep_versions, trash_keep_hours, trash_max_mb in kareladb.conf); the Keep data page frees them at once.
Open forhow long ago the server opened this database

A database with deferred triggers also shows Deferred trigger queues, one line per trigger:

ColumnWhat it means
Trigger, Tablethe trigger and the table it watches
Waitingjobs not finished yet
Laghow long the oldest waiting job has waited (- when none waits)
Runningthe job running now and its rows, or -
Failed joba job that failed and stopped the queue, with its error. Fix the cause, then run RETRY TRIGGER QUEUE <trigger>.

The same numbers come from GET /api/trigger-queue, which can also wait until the jobs are done.

Tables opens a line per table:

ColumnWhat it means
Rowsrows saved in partition files
In memoryhow much of that table's data is in memory now
Partitions / Loadedhow many partitions the table has, and how many are in memory
Not yet writtenrows changed since the last checkpoint

This is the quickest way to see which table is using the memory budget, and whether a big load has been written to disk yet.

Server activity

The terminal at the bottom of the Home page shows what the server has done lately, newest at the bottom: every statement that ended, every bulk load and where it came from, timer runs, deferred trigger jobs, logins and backups. It reads GET /api/activity, described here.

KindOne event for
querya statement over HTTP (/exec, /exp, /cursor) or the PostgreSQL port, when it ends
writea POST /write (line protocol) or POST /imp (CSV import) request: its rows and tables
timera run of a timer
triggera job of a deferred trigger that finished or failed (client (deferred trigger))
logina login that worked, a failed login, a lockout
backupa backup made from the console or the backup schedule
serverthe server started or stops
  • It is kept in memory only: the last 5,000 events (kareladb serve --activity-log-size N, 0 turns it off). A restart starts it empty. For a record that is kept, use the audit log.
  • Passwords, secrets and tokens in SQL show as '***', and long statements are cut to 300 characters.
  • A bulk load is one event per request, never one per row, so logging does not slow loading down.
  • Requests with the header X-KDB-Quiet: 1 are not logged. The console sends it with its own background refreshes.

Syntax:

GET /api/activity[?after=<seq>][&limit=<n>][&db=<name>]
ParameterMeaning
afteronly events with a larger seq. Leave it out for the newest events.
limitat most this many events (default 500, at most 2000)
dbonly events of this database

The reply is {"seq", "dropped", "events"}. seq is the newest event's number: send it back as after to get only what is new. dropped is true when some events after after were already pushed out of memory.

Event fieldMeaning
seq, msits number, and when it happened (Unix milliseconds)
kind, levelsee the table above; level is info, ok or error
userwho did it; empty for the access token
clientwhere it came from: 10.0.0.5 (pg), 127.0.0.1 (http), (timer refresh_prices)
database, textthe database, and the statement or a message like 12,000 rows into trade_log (line protocol)
rows, took_ms, errorrows changed or returned (-1 = not known), how long it took, and the error

An admin (or the token) sees every event; any other user sees only their own.

What it does not show

  • Numbers of the past: the panel keeps nothing, so a reload starts fresh. For a history, let Prometheus read GET /metrics, or read /api/stats from a script every minute and keep the rows in a table.
  • Statements that finished long ago. The activity keeps only the recent ones in memory; the audit log (SHOW AUDIT) keeps who changed what.
  • Damage and backups; those are in the Health panel on the right side of the console and in /api/info.
