CSV import over HTTP (POST /imp)

Send a CSV file to kareladb serve and it loads the rows, making the table from the file when it is new - QuestDB's /imp.

  • Category: HTTP API
  • Keywords: /imp, imp, CSV import, timings, Server-Timing, parse_ms, lock_wait_ms, wal_ms, apply_ms, durable_ms, durable, queued, gzip upload, import CSV, upload CSV, load a file, QuestDB import, multipart, form-data, overwrite, atomicity, skipCol, skipRow, abort, forceHeader, partitionBy, delimiter, fmt, rowsImported, rowsRejected, schema
  • See also: Line protocol (POST /write), Loading many rows, Run SQL over HTTP (/exec, /exp), HTTP API overview, CREATE TABLE, Partitions, SORT BY and DEDUP KEY

POST /imp loads a CSV file into a table. It is QuestDB's import route, so a QuestDB script or the QuestDB web console can send here without changes.

  • A table that is not there yet is made from the file: the column names come from the first line, the types from the values.
  • A table that is there gets the rows added (upserted, like the line protocol).
  • Everything is written in one transaction: after a good answer all rows are in, after an error nothing changed.

For SQL, use POST /exec. For a fast live feed, use the line protocol. More ways to load data: loading data.

POST /imp

Syntax:

POST /imp?name=<table>[&db=<name>]
         [&overwrite=true][&atomicity=skipCol|skipRow|abort]
         [&timestamp=<column>&partitionBy=DAY|MONTH|YEAR|NONE]
         [&delimiter=,][&forceHeader=true][&fmt=json]
body: the CSV itself, or multipart/form-data with a file part named "data"

Reads the CSV, makes the table when it is new, and writes the rows.

ParameterWhereMeaningDefault
nameURLThe table to load into. Without it, the file name of the upload (without .csv) is used.required
dbURLThe database (or the header X-KDB-Database). Without it: the one database that already has the table (which database).see the left
overwriteURLtrue: drop the table first and make it again from the file.false
atomicityURLWhat a value that does not fit its column does: skipCol the value becomes NULL, skipRow the whole row is left out, abort nothing at all is written.skipCol
dedupURLskip: no duplicate lookups in days that already hold rows. A key already stored may then be there twice; the answer has dedupSkipped (dedup=skip).on
timestampURLWhich column is the time column of a new table (TIMESERIES(...)).none
partitionByURLNONE, DAY, MONTH or YEAR for a new table. Anything but NONE needs timestamp=.NONE
delimiterURLThe character between the values; \t or tab for a tab. Without it KarelaDB guesses from the first lines.guessed
forceHeaderURLtrue: the first line is column names. Without it KarelaDB decides: names that match the table, or a first line with nothing that looks like data.guessed
fmtURLjson: answer as JSON. Anything else: a short text answer.text
schemaform partJSON that sets column types: [{"name": "close", "type": "DOUBLE"}].types guessed
Answer (with fmt=json)Meaning
status"OK", or the error message
databasethe database the rows went into
locationthe table the rows went into
rowsImportedhow many rows were written
rowsRejectedhow many rows were left out (atomicity=skipRow)
headerwhether the first line was read as column names
partitionBy, timestampthe table's partitioning and time column
columnsone entry per column: name, type, size in bytes, errors (values that did not fit)
timingswhere the time of the request went, in milliseconds (timings)
  • Status codes: 200 loaded (read rowsRejected: a 200 can still have left rows out); 400 a bad CSV, a bad parameter, an unknown column, atomicity=abort with a bad value, or no db when the database cannot be worked out; 401/403 login or role (403 also when a table right does not allow inserts into this table); 404 unknown database; 405 for a GET; 408 a trigger ran past the statement timeout; 413 body over 64 MB (counted after unpacking); 500 server trouble (nothing written); 503 while the server is stopping; 507 the disk is full: free space, then send the same file again, unless the message says do not send it again (the disk filled while the log was flushed: the rows are already in the table and are saved once space is back, see backup and safety).
  • Roles: loading into a table that is there needs the write role. Making a table (a new name, or overwrite=true) needs admin.
  • Types of a new table: BOOLEAN, LONG, DOUBLE, DATE, TIMESTAMP, else STRING. Send schema (or make the table yourself with CREATE TABLE) when you want SYMBOL, DECIMAL(2) or a PRIMARY KEY.
  • Notes:
    • Rows are upserted: a row with the same PRIMARY KEY or DEDUP KEY replaces the old one, so sending the same file twice makes no duplicates.
    • The first 5000 lines are read first, to find the header and the types. A column whose later values do not fit follows atomicity.
    • The body may be compressed with Content-Encoding: gzip or deflate. The 64 MB limit counts the unpacked CSV. A damaged body gives 400 and imports nothing. With curl: gzip -c prices.csv | curl --data-binary @- -H "Content-Encoding: gzip" "http://127.0.0.1:9900/imp?name=prices".
    • Triggers run once for the whole request, like the line protocol. Their time counts toward the statement timeout; send X-KDB-Statement-Timeout for a longer one (admins only). A trigger that runs too long gives status 408 and trigger <name>: statement timeout (<N> s) (nothing was imported).

When the OK comes, and where the time went

An OK from /imp (200) or /write (204) means the rows are written and safe on disk. Nothing is queued for later: the answer waits for the log's disk sync. A server crash right after the OK loses none of these rows.

Each answer says where its time went. /imp with fmt=json has a timings object; /write answers 204 with no body, so it sends the same numbers in the standard Server-Timing header (browser developer tools show it). All are milliseconds with 3 decimals.

FieldServer-TimingWhat the time was spent on
parse_msparsereading the body (after unpacking gzip) and building the rows, before any lock
lock_wait_mslockwaiting behind other writes of the same tables, or for a transaction that holds one
wal_mswalwriting the log and waiting for its disk sync. Writers that arrive together share one sync
apply_msapplychecking the rows (keys, rules) and putting them in the table
trigger_mstriggertriggers the rows fired inside the request
durable_msfrom the start until the rows were on disk: the moment the OK can go out
total_mstotalthe whole request

The five steps add up to total_ms. A slow load then shows at a glance what to fix:

  • a large lock_wait_ms: other writers or a long transaction hold the table. Send fewer, bigger requests, or write to separate tables.
  • a large wal_ms: the disk is slow to sync. Bigger requests share one sync between more rows.
  • a large parse_ms: the body is big. Several senders at once parse in parallel.

The activity log (GET /api/activity) keeps the same numbers for each write event, and GET /api/stats adds them up since the start under writes (line_protocol and csv_import: requests, rows and the sum of each step; a step's average is its sum divided by requests). bench/parallel-write.mjs sends from 1, 2, 4 and 8 senders at once and prints rows per second with the average of each step.

Which database, without db=

A QuestDB client has no db= to send, so /imp works out the database from the table name:

The server hasWithout db= the rows go to
one databasethat database
several, and one of them has the tablethat database (the default one wins when it is among several that have it)
several, and more than one has the table (not the default)nothing: 400, add db=
several, and none has the tablenothing: 400, add db= or create the table first

KarelaDB refuses rather than guessing, so a load meant for another database never makes a new table with guessed types in the default one. The answer's database says where the rows went.

Clients (not run by the help build):

# QuestDB's own way: a multipart upload with a file part named "data".
curl.exe -s -F "data=@day_closes.csv" `
  "http://127.0.0.1:9900/imp?name=day_closes&timestamp=time&partitionBy=YEAR&fmt=json&db=market"
import requests

with open("day_closes.csv", "rb") as f:
    r = requests.post("http://127.0.0.1:9900/imp",
                      params={"name": "day_closes", "timestamp": "time",
                              "partitionBy": "YEAR", "fmt": "json", "db": "market"},
                      files={"data": ("day_closes.csv", f, "text/csv")})
answer = r.json()
if answer["status"] != "OK":
    raise RuntimeError(answer["status"])
print(answer["rowsImported"], "rows in", answer["location"])
