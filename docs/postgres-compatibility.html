PostgreSQL compatibility matrix

One row per PostgreSQL feature - protocol, statements, queries, types, functions, catalogs - saying whether it works and is tested, works with a difference, or is refused, and which test file covers it.

  • Category: Postgres protocol
  • Keywords: postgresql compatibility, compatible with PostgreSQL, PostgreSQL support, compatibility matrix, supported, not supported, refused, differences from PostgreSQL, PostgreSQL features, what works, what does not work, migrate from PostgreSQL, ORM, Prisma, SQLAlchemy, Django, JDBC, extensions, pg_stat, ON CONFLICT, REPEATABLE READ, NUMERIC, schemas, inheritance, partitioning, tablespace, EXCLUDE, DEFERRABLE, tsvector, range types, hstore, PostGIS, COPY, LISTEN, logical replication, SCRAM, md5
  • See also: PostgreSQL protocol (port 8832), Transactions, Column types, Limits, PostgreSQL-compatible functions, Time and time zones, The procedure language

KarelaDB is not PostgreSQL. It speaks PostgreSQL's wire protocol on port 8832 (PostgreSQL protocol) and understands a large part of PostgreSQL's SQL. This page says, feature by feature, what you can expect. It was written from the program's code and tests on 2026-10-25, and every statement marked by hand was run on a build of that day.

How to read the tables

MarkMeaning
YesWorks as in PostgreSQL, and an automated test covers it (the file is in the last column).
Yes, by handWorks as in PostgreSQL. It was run by hand on 2026-10-25, but no automated test is named for it. It can still break without a test failing.
DiffersWorks, but the answer, the rules or the limits are not PostgreSQL's. The column says how. Read it before you move an application.
RefusedKarelaDB refuses it with an error that names the problem. Nothing is run and nothing is saved. A few rows say accepted and ignored: the statement is accepted so that tools do not stop, and does nothing.

The tests are in tests/. test_pg*.cpp run a real PostgreSQL client against a real server. tests/pg_go/main.go (the pgx driver) and tests/pg_python/check_pg8000.py (the pg8000 driver) are run by hand against a server.

Settings that change the answers

Three settings make KarelaDB answer like PostgreSQL where it does not by default. All are off by default and do not change anything while off.

SettingEffectDetails
SET kdb.pg_compat = on (or --pg-compat on, or ALTER DATABASE ... SET pg_compat = on)PostgreSQL 14's answers: exact decimal literals and ::numeric, RANGE window frames, PostgreSQL's NULL order in windows, en_US text order, a plain TIMESTAMP as the session's wall clockPostgreSQL-compatible results
SET int_division = integer (or --pg-int-division on)whole number / whole number gives a whole numberinteger division
--pg-timestamptzTIMESTAMP columns are sent as timestamptztimes

How this page was made

  1. The protocol rows come from src/server/pg_server.cpp and tests/test_pg.cpp.
  2. Each statement, type, function and catalog row was run by hand with kareladb sql on a build of 2026-10-25, and the result recorded: it ran, or it gave the error quoted. A row with by hand has no test file in tests/ that names the feature.
  3. Each test file was found by searching tests/ for the feature's words. A file listed covers the feature, not necessarily every detail of it.
  4. The differences come from the code and from limits, known limitations and tutorial chapter 22.

If a row is wrong or out of date, the program wins: test the statement. When a feature is added or removed, change its row in the same commit.
